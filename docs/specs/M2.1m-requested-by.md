# M2.1m — A coluna do autor do pedido

**Bloco:** Marco 2 · M2.1m · frente `marco1` — a metade da `marco1` no M2.1a
**Status:** 🟡 escrita em 2026-09-29 · revisão adversarial (entrega contrato entre frentes, PROCESSO §4): a rodada 1 reprovou (1 grave, 1 médio, 5 leves), tudo absorvido; a confirmação aprovou · ✅ **aprovada pelo dono da frente** (2026-09-29)
**Plano:** [`planos/M2.1m-requested-by.md`](../planos/M2.1m-requested-by.md)
**Ramo:** `marco1/M2.1m-requested-by`

---

## Problema

O [RF-26 do M2.1a](M2.1a-identidade-e-acesso.md#rf-26) quer que o pedido de cálculo sob demanda e a `risk_run` que
ele abre guardem quem pediu. A `gold.risk_run` já tem a coluna `requested_by`, sempre nula; o pedido,
`core.compute_request`, **não tem coluna nenhuma para isso**. O modelo (`backend/apps/api/models.py`) e as migrations
(`backend/apps/api/migrations/`) são da `marco1`, e ninguém cria migration em app de outra frente
([FRENTES.md](../FRENTES.md#cercas)). Por isso a T14 do M2.1a — o código que preenche a coluna — está parada
([plano do M2.1a, *Pré-condição externa*](../planos/M2.1a-identidade-e-acesso.md#pré-condição-externa--a-coluna-requested_by)).

## Resultado esperado

`core.compute_request` tem a coluna `requested_by_id`, chave estrangeira para `core.user`, anulável, na `main`. As
linhas existentes ficam nulas. Nada mais muda: nenhum caminho do código a preenche, a API responde igual, e a T14 do
M2.1a pode começar.

## Escopo

### Dentro

- O campo `requested_by` em `ComputeRequest`, literal do contrato do M2.1a.
- A migration `0002` de `apps/api`, gerada pelo `makemigrations`.
- Um teste que prova a coluna no banco e o `PROTECT`.

### Fora

- **Preencher a coluna**: a view do `POST`, a abertura em `apps/risk/tasks.py`, o `open_run` e o `_manifest` são da
  T14 do M2.1a, frente `identidade`, revisada pela `marco1`.
- `gold.risk_run.requested_by`: já existe desde o F2a; nada muda nela.
- Expor o autor na API: o `ComputeRequestSerializer` lista os campos um a um, e o autor não entra. Quem pediu não é
  dado público do `GET /risk`.
- Migration de dado: os pedidos antigos legitimamente não têm autor.

## Requisitos

<a id="rf-01"></a>**RF-01** — **O campo.** Em `ComputeRequest`, `backend/apps/api/models.py`:

```python
requested_by = models.ForeignKey(
    settings.AUTH_USER_MODEL,
    on_delete=models.PROTECT,
    related_name="compute_requests",
    null=True,
)
```

É o literal do contrato ([plano do M2.1a, linha do contrato](../planos/M2.1a-identidade-e-acesso.md#pré-condição-externa--a-coluna-requested_by)).
O `PROTECT` segue o de `RiskRun.requested_by` e não trava a gestão de usuários: o M2.1a desativa (`is_active`), não
apaga (`apps/accounts/services.py`). O docstring da classe ganha uma frase sobre a coluna: nula para o pedido anônimo
e para todo pedido anterior ao M2.1a.

<a id="rf-02"></a>**RF-02** — **A migration.** `backend/apps/api/migrations/0002_compute_request_requested_by.py`,
saída do `makemigrations api --name compute_request_requested_by`, com a dependência do usuário pelo
`swappable_dependency`. Só `AddField`: nenhuma migration existente é alterada, e nenhuma de outra app.

<a id="rf-03"></a>**RF-03** — **A API não muda.** O corpo do `GET /api/v1/assets/{ticker}/risk` e o esquema OpenAPI
seguem iguais: `tests/api/test_risco.py` confere o conjunto exato das chaves do pedido (`CHAVES_PEDIDO`), e o esquema
segue sem aviso.

## Verificação

Todo comando roda no contêiner `worker`, de `/repo/backend` (`W` = `docker compose exec -T worker`), com o Beat parado.

| V | RF | Como se prova |
|---|---|---|
| V-01 | RF-01 | teste novo: `information_schema.columns` de `core.compute_request` tem `requested_by_id`, `bigint`, `is_nullable = YES` — no molde de `tests/accounts/test_api_key_modelo.py` |
| V-02 | RF-01 | teste novo: pedido com autor, `user.delete()` → `ProtectedError`, **com o pedido em `erro.value.protected_objects`** — o `User` tem outros vínculos `PROTECT` (`AccessEvent`, `ApiKey`), e o erro não pode vir deles; pedido criado sem autor → `requested_by_id is None` |
| V-03 | RF-02 | `W python manage.py makemigrations --check --dry-run` sem mudança; `W python manage.py migrate` no banco de dev aplica só a `api.0002` (premissa: o banco de dev em dia com a `main` antes); `git diff --stat` em `apps/*/migrations/` mostra só o arquivo novo |
| V-04 | RF-03 | `tests/api/test_risco.py` verde sem mudança (o `CHAVES_PEDIDO`); `tests/accounts/test_esquema_openapi.py` verde sem mudança |
| V-05 | todos | a suíte inteira, `W mypy`, `W ruff check .` e `W ruff format --check .` limpos |
| V-06 | RF-01, RF-03 | mutações, cada uma revertida: (a) sem o `null=True` **no modelo e na `0002`** — quem cria a coluna no banco de teste é a migration, então mudar só o modelo passa vazio ([aprendizados](../aprendizados.md), "O esquema no `db_table` mora em dois lugares") — o V-01 reprova pelo `is_nullable = NO` e o pedido sem autor do V-02 por `IntegrityError`; (b) `CASCADE` no lugar do `PROTECT`, só no modelo (o `on_delete` é do Django, não do banco) → o V-02 reprova; (c) `"requested_by"` em `ComputeRequestSerializer.Meta.fields` → `test_risco.py` reprova no `CHAVES_PEDIDO` |
