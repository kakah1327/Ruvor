## Como ler este plano

[PROCESSO §5](../PROCESSO.md#5-anatomia-de-um-plano): contratos, não corpos. Literal só no campo (é o contrato com a
`identidade`) e nas mutações (a falha é silenciosa).

**Todo critério roda no contêiner `worker`**, de `/repo/backend`. O atalho `W` é `docker compose exec -T worker`.
Critério **padrão** de toda tarefa, além do próprio:

```
W pytest tests ; W mypy ; W ruff check . ; W ruff format --check .
```

com o Beat parado (`docker compose stop beat`), como no fecho do M1.6c. **Uma suíte por vez no `worker`**: outro
agente trabalha em paralelo nesta frente, e duas suítes no mesmo `worker` usam o mesmo banco de teste
([aprendizados](../aprendizados.md), "Duas suítes no mesmo `worker` usam o mesmo banco de teste"). Antes da suíte
inteira, confirmar com o humano que a do outro agente não está rodando. Durante a tarefa, rodar só `tests/api`.

**Implementar no checkout principal**, não em worktree: o `compose.yaml` monta o checkout principal
([aprendizados](../aprendizados.md), "O worktree não é o que o contêiner monta").

`git add` pelos caminhos, nunca `git add backend` ([aprendizados](../aprendizados.md), "`git add backend` falha pelo
`backend/nul`").

## Tarefas

### Tarefa 1 — O campo e a migration (RF-01, RF-02, RF-03)

**Depende de:** — · **Visual:** não

**Arquivos**
- altera: `backend/apps/api/models.py`
- cria: `backend/apps/api/migrations/0002_compute_request_requested_by.py`
- cria: `backend/tests/api/test_autor_do_pedido.py`

**Contrato** — o campo, literal (spec RF-01), em `ComputeRequest`, depois de `risk_run`:

```python
requested_by = models.ForeignKey(
    settings.AUTH_USER_MODEL,
    on_delete=models.PROTECT,
    related_name="compute_requests",
    null=True,
)
```

com `from django.conf import settings` entre os imports. O docstring de `ComputeRequest` ganha uma frase: `requested_by`
é quem pediu, nulo para o pedido anônimo e para todo pedido anterior ao M2.1a; quem o preenche é a view do `POST`
(T14 do M2.1a).

A migration sai de `W python manage.py makemigrations api --name compute_request_requested_by`, e logo depois
`W ruff format apps/api/migrations/0002_compute_request_requested_by.py`. Esperado: um `AddField` e as dependências
`("api", "0001_compute_request")` e `migrations.swappable_dependency(settings.AUTH_USER_MODEL)`. Qualquer outra
operação (em especial sobre índice ou restrição com esquema no `db_table`) é sinal de erro: para e escala.

**Critério de aceite**
- `test_autor_do_pedido.py`, `pytestmark = pytest.mark.django_db`:
  - **V-01:** `information_schema.columns` com `table_schema = 'core' AND table_name = 'compute_request'` tem
    `requested_by_id` com `data_type = 'bigint'` e `is_nullable = 'YES'`.
  - **V-02:** pedido com autor → `user.delete()` levanta `ProtectedError`, e o pedido está em
    `erro.value.protected_objects`; pedido criado sem `requested_by` → `requested_by_id is None` depois do
    `refresh_from_db()`.
- **V-03:** `W python manage.py makemigrations --check --dry-run` sai 0 sem mudança; `W python manage.py migrate`
  no banco de dev aplica só `api.0002` (premissa: o banco de dev em dia com a `main`); `git status --short backend/apps`
  mostra só `models.py` e a `0002` nas apps.
- **V-04:** `tests/api/test_risco.py` e `tests/accounts/test_esquema_openapi.py` verdes **sem mudança**.
- **V-06**, cada mutação aplicada, medida e revertida, com o resultado no relato:
  - (a) sem o `null=True` no modelo **e** na `0002`, (o `pyproject.toml` não usa `--reuse-db`: o banco de teste nasce das migrations a cada rodada) → o V-01 reprova
    (`is_nullable = NO`) e o pedido sem autor do V-02 reprova por `IntegrityError`;
  - (b) `CASCADE` no lugar do `PROTECT`, só no modelo → o V-02 reprova;
  - (c) `"requested_by"` em `ComputeRequestSerializer.Meta.fields` → `test_risco.py` reprova no `CHAVES_PEDIDO`.
- Critério padrão (V-05).

**Cerca de escopo:** nenhum código preenche a coluna — a view do `POST`, `apps/api/ondemand.py`, `apps/risk/` e
`apps/assets/tasks.py` não mudam (T14 do M2.1a). Nenhuma migration existente muda. O serializador não muda.
