## Como ler este plano

Segue o [PROCESSO §5](../PROCESSO.md#5-anatomia-de-um-plano): **contratos, não corpos**. Entra
conteúdo literal em três lugares, e só neles:

1. **Onde o conteúdo é o contrato** — os `db_table` e as `dependencies` das migrations, o
   regex de código de ação, os rótulos do relatório, a lista de fixtures, a forma do cliente
   falso.
2. **Onde a lógica é sutil e a falha é silenciosa** — a migration de dados do Ibovespa
   (idempotência), a guarda de rede do `conftest.py` (o ponto de patch decide se ela
   funciona), a sequência coleta → transação → `failed` fora da transação, e a regra de
   *upsert* que avança `last_seen_run` sem tocar em `updated_at`.
3. **Em nada mais.** Corpos de modelo, de cliente, de conformação e de teste não entram: a
   spec fixa campos e comportamento, e `apps/accounts` é o padrão a imitar.

Toda tarefa é executável por alguém que nunca participou da conversa. Todo critério de aceite
roda **dentro do contêiner `web`**, como o F3 fixou ([D-33](../decisoes/D-33-dia-a-dia-dentro-do-conteiner.md)).

Decisões que a spec deixou em aberto de propósito, tomadas aqui para que nove tarefas não as
derivem de nove jeitos:

| Decisão | Valor |
|---|---|
| Rótulo do app | `assets` |
| Nomes dos modelos | `CollectionRun`, `B3CompanyListing`, `B3CompanyDetail`, `Asset` |
| Enumerações | `TextChoices`: `CollectionRun.Status` (`RUNNING="running"`, `OK="ok"`, `FAILED="failed"`), `Asset.Kind` (`STOCK="stock"`, `INDEX="index"`), `Asset.Status` (`ACTIVE="active"`, `INACTIVE="inactive"`) |
| `related_name` das FKs para `CollectionRun` | `listings`, `details`, `first_seen_assets`, `last_seen_assets` |
| Exceções | `B3ClientError(Exception)` em `b3.py` — qualquer falha do cliente depois das tentativas, inclusive `totalPages: null`; `CollectionFailed(Exception)` em `importer.py` |
| Construtor do cliente | `B3Client(timeout: float = 30.0, sleep: Callable[[float], None] = time.sleep)` |

| `ImportReport` | `dataclass(frozen=True)` em `importer.py`; campos `listed`, `pages`, `consulted`, `conformed` (tamanho do dicionário `ticker → ConformedAsset`, isto é, ações ativas ao fim da coleta), `created`, `updated`, `inactivated`, `reactivated`, `empty_details`, `quoted_without_code`, `odd_classifications`; método `render() -> str` produz o relatório da spec |
| O `now()` da coleta | um único `timezone.now()` capturado no início da conformação; é o que vai em `created_at`/`updated_at` de toda linha tocada nessa coleta |
| Ordem de inserção na `bronze` | `bulk_create` por página de listagem; detalhe um a um, na ordem da listagem |
| Cliente falso | `FakeSource(pages: list[list[dict]], details: dict[str, dict], *, fail_listing: bool = False, fail_on: str \| None = None)` em `tests/assets/conftest.py`, com `calls: list[str]` registrando os `code_cvm` pedidos. `fail_listing` faz `list_companies()` levantar `B3ClientError("fonte falsa: falha na pagina 2")` na segunda página (o cenário precisa ter duas); `fail_on` faz `get_company(code)` levantar `B3ClientError(f"fonte falsa: falha em {code}")` quando `code == fail_on` — é assim que RF-02 e RF-10 simulam falha da fonte. `code_cvm` fora de `details` levanta `AssertionError` — cenário mal montado é erro do teste, não `{}`. **Atenção:** `run_import` converte qualquer exceção em `CollectionFailed`; num teste que espera falha, um cenário mal montado passa verde. Todo teste que espera falha assert também a **mensagem**: `run.error` começa com `B3ClientError: fonte falsa` nos de fonte, e contém os dois `code_cvm` no RF-16 |
| Nome dos testes | `test_rfNN_<descricao>` para todo teste que prova um requisito; os `-k` das mutações (T8) dependem disso |
| Estilo de import nos pontos de patch | `importer.py` faz `from apps.assets.conform import conform_company`; `import_assets.py` faz `from apps.assets.b3 import B3Client`. Com `from apps.assets import conform`, o `monkeypatch.setattr("apps.assets.importer.conform_company", ...)` levanta `AttributeError` — é o simétrico do `urlopen` |
| Onde ficam os testes do cliente real | `tests/assets/test_b3_client.py`, com `urlopen` **falso** injetado pelo `monkeypatch` em `urllib.request.urlopen` (o mesmo ponto que a guarda usa) |

**O que este plano NÃO decide:** nada sobre endpoint, agendamento, cobertura ou preços —
tudo de outros blocos, por decisão registrada na spec.

from django.db import migrations
from django.db.backends.base.schema import BaseDatabaseSchemaEditor
from django.db.migrations.state import StateApps
from django.utils import timezone


def cria_ibovespa(apps: StateApps, schema_editor: BaseDatabaseSchemaEditor) -> None:
    Asset = apps.get_model("assets", "Asset")
    now = timezone.now()
    Asset.objects.get_or_create(
        ticker="IBOV",
        defaults={
            "kind": "index",
            "name": "Índice Bovespa",
            "trading_name": "IBOVESPA",
            "status": "active",
            "provider_symbol": "^BVSP",
            "created_at": now,
            "updated_at": now,
        },
    )


def remove_ibovespa(apps: StateApps, schema_editor: BaseDatabaseSchemaEditor) -> None:
    Asset = apps.get_model("assets", "Asset")
    Asset.objects.filter(ticker="IBOV").delete()


class Migration(migrations.Migration):
    dependencies = [("assets", "0001_bronze_e_silver_asset")]

    operations = [migrations.RunPython(cria_ibovespa, remove_ibovespa)]

### Tarefa 6 — O `importer`: coleta, transação e *upsert*

**Depende de:** T3, T4, T5
**Visual:** não

**Arquivos**
- cria: `backend/apps/assets/importer.py`, `backend/tests/assets/test_importer.py`

**Contrato**

`CompanySource` (`Protocol`), `CollectionFailed`, `ImportReport` (tabela de decisões) e
`run_import(source: CompanySource) -> ImportReport`. A sequência é a da spec, e a parte sutil
entra literal — é onde uma versão errada passa verde na máquina de quem escreveu:

```python
def run_import(source: CompanySource) -> ImportReport:
    run = CollectionRun.objects.create(source="b3-listed-companies", started_at=timezone.now())
    try:
        listed, pages = _collect_listing(run, source)          # bulk_create por pagina
        details = _collect_details(run, source, listed)         # so type == "1"; grava {} tambem
        with transaction.atomic():
            report = _conform(run, listed, details)             # levanta CollectionFailed no RF-16
            run.status = CollectionRun.Status.OK
            run.finished_at = timezone.now()
            run.save(update_fields=["status", "finished_at"])
        return report
    except Exception as exc:
        # fora de qualquer transacao revertida: e por isso que o `failed` sobrevive
        run.status = CollectionRun.Status.FAILED
        run.error = f"{type(exc).__name__}: {exc}"  # o nome da classe e diagnostico na bronze
        run.finished_at = timezone.now()
        run.save(update_fields=["status", "error", "finished_at"])
        if isinstance(exc, CollectionFailed):  # o RF-16 ja levantou a certa
            raise
        raise CollectionFailed(run.error) from exc
```

`_conform`, o *upsert* — a regra que decide RF-07/RF-08/RF-09 e o significado de `updated_at`:

1. `now = timezone.now()` uma vez
2. conforma todas as companhias (T5); constrói `dict[ticker, ConformedAsset]`; se um ticker
   aparecer em duas companhias, levanta `CollectionFailed` com os dois `code_cvm` **antes de
   escrever** (RF-16)
3. carrega `Asset.objects.filter(kind=STOCK)` num `dict` por `ticker`
4. para cada ticker conformado:
   - não existe → `create` com `status=ACTIVE`, `first_seen_run=run`, `last_seen_run=run`,
     `created_at=now`, `updated_at=now` → conta em `created`
   - existe → compara as colunas conformadas (`isin`, `name`, `trading_name`, `cnpj`,
     `code_cvm`, `issuer_code`, `sector`, `subsector`, `segment`, `listing_segment`,
     `provider_symbol`); se alguma mudou, escreve e `updated_at=now` → conta em `updated`
     (só se a linha já estava `ACTIVE`); se `status` era `INACTIVE` → `ACTIVE`, conta em
     `reactivated` e escreve `updated_at=now` — `status` é coluna conformada, por simetria com o
     passo 5; **sempre** `last_seen_run=run`, e só isso não toca em `updated_at`
5. todo `Asset` `kind=STOCK` `ACTIVE` que não está no conformado → `status=INACTIVE`,
   `updated_at=now`, conta em `inactivated`; `last_seen_run` **não muda**
6. linhas `kind=INDEX` nunca são lidas nem escritas

`ImportReport.render()` produz exatamente estas quatro linhas, com estes rótulos:

```
listagem: {listed} companhias em {pages} paginas
consultadas (type=1): {consulted}
acoes conformadas: {conformed} (criadas {created}, alteradas {updated}, inativadas {inactivated}, reativadas {reactivated})
casos de borda: detalhe vazio {empty_details}, hasQuotation=S sem codigo de acao {quoted_without_code}, classificacao fora de tres partes {odd_classifications}
```

`test_importer.py` — todos com `@pytest.mark.django_db` e `FakeSource`, cenários compostos
de itens reais (spec, "Fixtures"): RF-02 (falha de fonte → `failed` + `CollectionFailed`;
conformação que levanta via `monkeypatch` em `apps.assets.importer.conform_company` →
`failed`); RF-03 (payload da listagem e do detalhe `==` fixture; `{}` gravado); RF-04
(`source.calls` só tem os `type == "1"`; o cenário **inclui ao menos um item `type == "7"`**
da página 1 — sem ele a mutação 6 passa); RF-06 (`IntegrityError` ao criar segundo `PETR4`,
dentro de `transaction.atomic()` próprio); RF-07 (segunda coleta: linhas iguais exceto
`last_seen_run`, `updated_at` igual, `last_seen_run` = coleta 2 em todas as ativas `kind=stock`
— `IBOV` é ativa com `last_seen_run` nulo); RF-08 e
RF-09 (três coletas: `PETR3` some e volta); RF-10 (`fail_on` no segundo detalhe, com **`PETR` como primeiro** — uma companhia que
produz ações, senão a mutação 2 passa: `Asset` antes == depois; a `bronze` tem o detalhe de
`PETR`); RF-12 (`IBOV` intocado após
coleta, inclusive `updated_at`); RF-13 (`render()` com números assertados); RF-16 (`CSNA`
