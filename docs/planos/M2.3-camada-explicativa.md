### Onde cada comando roda

**Regra comum aos planos desta frente escritos em worktree.** O `compose.yaml` monta `./frontend`, `./brand/ruvor` e
`./docs/mockups` **do checkout principal** (`E:/Temp/Trilobit/varlab`), não do worktree
([aprendizados](../aprendizados.md), "O worktree não é o que o contêiner monta"): `docker compose exec frontend npm
test` roda o código de lá. Duas saídas, nesta ordem de preferência:

1. **Contêiner avulso com o worktree montado por cima**, do checkout principal:

   ```sh
   WT=E:/Temp/Trilobit/varlab-wt/M2.3-camada-explicativa
   MSYS_NO_PATHCONV=1 docker compose run --rm --no-deps \
     -v "$WT/frontend:/repo/frontend" \
     -v "$WT/brand/ruvor:/repo/brand/ruvor:ro" \
     -v "$WT/docs/mockups:/repo/docs/mockups:ro" \
     frontend sh -c "<guarda> && <comando>"
   ```

   O `node_modules` vem do volume anônimo que o serviço declara (`/repo/frontend/node_modules`), recriado da imagem
   pelo `run` — o do worktree, que não existe, não o esconde.
2. **O checkout principal**, com `docker compose exec -T frontend sh -c "<guarda> && <comando>"`, **só com a
   confirmação do orquestrador de que o checkout principal está neste ramo** — ele é usado por outro agente.

**Quando a tarefa precisa do stack servindo o ramo** — um mockup no portão, a tela no navegador, a execução real —, o
contêiner avulso não basta, porque o serviço `frontend` e a `web` servem o checkout principal. O `git switch` do ramo
no checkout principal é **recusado** pelo Git, porque o ramo está em uso no worktree. Então **o orquestrador**:

1. confirma que ninguém está usando o checkout principal;
2. se a `main` avançou (o M1.6d entra antes: é pré-condição), faz o merge da `main` **no ramo, no worktree**, antes;
3. põe o checkout principal em `git switch --detach <HEAD do ramo>` — o que o stack precisa servir (o mockup, o
   código da tarefa) já **commitado** no ramo, porque o destacado só vê commits;
4. ao fim da tarefa, volta o checkout principal ao ramo em que estava.

**Os commits continuam no worktree**; o checkout principal destacado só serve o stack.

**A guarda.** Todo critério de aceite começa por ela, para o Vitest não rodar só os arquivos velhos e sair verde:
`test -f tests/<o arquivo que a tarefa cria>` quando a tarefa cria um teste; quando não cria, `grep -q "<um trecho que
a tarefa escreveu>" <arquivo>`. **Guarda que falha é critério que falha.**

| O quê | Comando dentro do `sh -c` (diretório `/repo/frontend`) |
|---|---|
| um arquivo de teste | `npm test -- tests/<arquivo>` |
| a suíte, o lint, os tipos, o build | `npm test` · `npm run lint` · `npm run typecheck` · `npm run build` |
| os mockups | o serviço `frontend` serve `docs/mockups/` do **checkout principal**, posto no HEAD do ramo pela regra acima; `http://localhost:<RUVOR_PORT_FRONTEND>/@fs/repo/docs/mockups/M2.3/<arquivo>.html`, com a API pelo proxy |
| a execução real | imagem oficial do Playwright, na rede do contêiner `frontend`, com o `docker run` de "A execução real" do [plano do M1.6b](M1.6b-as-telas.md) e as chaves da T15 |

**Este bloco não toca o backend.** A suíte do `worker` não roda em nenhuma tarefa — outro agente usa o `worker` —; a
T15 confere por `git diff --stat main -- backend/ engine/` vazio.

## O que este plano decide

### O módulo do nível — `frontend/src/reading.ts`

Literal na superfície; o corpo segue `theme.ts`.

```ts
export type Reading = "beginner" | "advanced";
export const READING_KEY = "ruvor-reading";

export function getReading(): Reading;              // a lembrada na primeira leitura; desconhecido ou erro → "beginner"
export function setReading(reading: Reading): void; // lembra (em try), aplica data-reading, avisa quem assina
export function onReadingChange(cb: (r: Reading) => void): () => void;
export function useReading(): Reading;              // useSyncExternalStore(onReadingChange, getReading, getReading)
export function resetReadingForTests(): void;       // só tests/: current = "beginner", limpa o armazenamento e data-reading

export function textFor<K extends LeituraKey>(key: K, reading: Reading): Leitura<(typeof TEXTOS)[K]>;
```

- **`getReading` aplica `data-reading` no `document.documentElement` na primeira leitura** (quando lê o armazenamento),
  e `setReading` a cada troca. Assim a marca existe desde a carga, antes de qualquer troca (a T1 testa).
- **`useReading` usa `useSyncExternalStore` com `getReading` como leitura síncrona** — o primeiro desenho já sai no
  nível lembrado, sem efeito e sem nada em `main.tsx` (RF-02, V-03). O `getServerSnapshot` também é `getReading`: é por
  ele que o `renderToString` do V-03 enxerga o nível lembrado. O `useState(getReading)` que o inventário da spec cita
  cumpre o mesmo papel; `useSyncExternalStore` o dispensa e acompanha a troca feita em outro ponto da página.
- `textFor` devolve `TEXTOS_AVANCADOS[key]` no avançado e `TEXTOS[key]` no iniciante. **Toda frase das 55 chaves passa
  por `textFor`**; o teste de seção do nível avançado ([A prova por seção](#a-prova-por-seção-no-nível-avançado)) pega
  a chave que ficou em `TEXTOS[...]`.

### O módulo das frases avançadas — `frontend/src/content/avancado.ts`

Literal no tipo, porque `TEXTOS` é `as const` (`textos.ts:646`) e a entrada de texto tem tipo literal — sem o
`Leitura<>`, a avançada teria de ser igual à iniciante letra por letra.

```ts
import type { TEXTOS, TextoKey } from "./textos";

/** Texto vira `string`; função mantém a assinatura (mesma chave, mesmos argumentos: RF-05). */
export type Leitura<T> = T extends string ? string : T;

/** As chaves já com frase avançada. Cresce seção a seção (T4, T7, T10, T13) até as 55 do RF-04. */
export const LEITURA_KEYS = [
  // …
] as const satisfies readonly TextoKey[];

export type LeituraKey = (typeof LEITURA_KEYS)[number];

export const TEXTOS_AVANCADOS: { readonly [K in LeituraKey]: Leitura<(typeof TEXTOS)[K]> } = {
  // …
};
```

**A avançada declara todos os parâmetros da iniciante, na mesma ordem**, inclusive os que não usa — com o prefixo
`_` (`(_negativo: boolean) => …`), que o Biome aceita como não usado de propósito. É o que mantém o `Function.length`
igual ao da iniciante (V-02) e o tipo satisfeito.

### A lista das 55 e as pendentes (V-02) — `frontend/tests/duas-leituras.test.ts`

A falha silenciosa é **uma chave que nunca ganha avançada e ninguém nota**. O teste, criado na T1:

- escreve **as 55 chaves do RF-04** numa constante `AS_55`, copiadas da spec (a T0 confere contra `textos.ts`);
- escreve `PENDENTES`, as que ainda não têm avançada — nasce com as 55;
- confere: `LEITURA_KEYS` ⊆ `AS_55`; `AS_55 − LEITURA_KEYS` **é exatamente** `PENDENTES` (nem mais, nem menos); para
  cada chave de `LEITURA_KEYS`, `TEXTOS_AVANCADOS[k]` existe e `typeof`/`Function.length` batem com `TEXTOS[k]`;
  `Object.keys(TEXTOS_AVANCADOS)` é exatamente `LEITURA_KEYS`.
- Cada tarefa de seção tira as suas de `PENDENTES`. **A T13 apaga a constante `PENDENTES`** e troca a conferência por
  `LEITURA_KEYS` igual a `AS_55`. O FECHA confere `grep -c PENDENTES frontend/tests/duas-leituras.test.ts` = 0.

Bloco irmão que acrescentar chave com frase antes do merge (o M3.3) entra em `AS_55` pela regra dos blocos irmãos da
spec — e o nome da constante muda com a contagem.

### A prova por seção no nível avançado

Cada tarefa de seção (T4, T7, T10, T13) acrescenta ao teste da seção um caso que **monta a seção no nível avançado**,
com a fixture da seção, e, **para cada chave da seção** na lista do RF-04:

- chave de texto: `TEXTOS[k]` **ausente** da seção e `TEXTOS_AVANCADOS[k]` **presente**;
- chave de função: a saída da avançada com os argumentos que a fixture produz **presente**, e a da iniciante com os
  mesmos argumentos **ausente**.

A chave que a fixture não exercita (um ramo que ela não tem) é declarada no teste, com o motivo, e coberta por outra
fixture da mesma seção. **Mutação obrigatória em cada tarefa de seção:** uma chave da seção volta a `TEXTOS[...]` no
componente → reprova.

### O recolhimento — `frontend/src/components/Collapsible.tsx`

```ts
type Props = {
  name: "moments" | "models" | "trail"; // vira data-collapsible
  label: string;                        // o texto do botão, de textos.ts
  children: ReactNode;
};
```

- **Aberto por padrão no avançado, fechado no iniciante**; trocar o nível reaplica o padrão (o estado local é
  reiniciado quando `useReading()` muda); abrir não é lembrado.
- Botão com `aria-expanded` e **`aria-controls` apontando para o id do conteúdo, que só existe aberto**. Escolha
  registrada: o conteúdo fechado não é renderizado (fora da árvore acessível e do fluxo), e com ele fechado o
  `aria-controls` aponta para um id ausente — o padrão de divulgação da WAI-ARIA admite isso, e os leitores ignoram a
  referência ausente. Não renderizar é **escolha**, não exigência do V-05: renderizar com `hidden` também tiraria o
  conteúdo da árvore acessível. Escolheu-se não renderizar para que a tabela e a trilha fechadas não custem desenho;
  os testes procuram pelo papel e pelo texto, e passam nas duas formas. A T7 registra em "Correções" se o Biome ou um
  teste de acessibilidade pedir outra forma.
- O raiz tem `data-collapsible={name}` e `data-open`.
- **Nunca dentro de elemento com `aria-live`** (V-05).
- **As linhas de teste da tabela** não usam `Collapsible`: seguem o estado que já existe em `ModelTable`
  (`useState<ReadonlySet<ModelName>>`, `ModelTable.tsx:189`, na função que começa em `:186`). O conjunto inicial é
  vazio no iniciante e os nove no avançado, reiniciado quando o nível muda. **Cada linha expansível** leva
  `data-collapsible="tests"` e o seu `data-open` — nove marcas, uma por modelo.

### A expressão da D-64 (V-06) — `frontend/tests/d64.test.ts`

As duas expressões aprovadas no portão da T9 — uma para `risco.veredito`, uma para `risco.naoRejeitados` — ficam

- **O laço de palavras proibidas** (o `it` de `vocabulario.test.ts:293`, que hoje percorre `TEXTOS` com `EXEMPLOS`)

- A varredura do texto-fonte já pega `avancado.ts` (ela lê todo `src/content/` menos `ressalva.ts`) — a T1 confere.
- **A regra `pior`/`piores` da seção Fundamentos** (`fundamentos.test.tsx`) passa a valer também sobre as saídas de

### O nível nos testes que já existem

Com o padrão iniciante, testes do M1.6b e do M1.6c que procuram o recolhido (a assimetria, a tabela, a trilha, as
linhas de teste) passam a não achar. **Cada tarefa de seção ajusta os testes da sua seção**, declarando o nível com o

### A conferência técnica — um arquivo por seção

A frase avançada afirma como o número é calculado; afirmação errada passa por todas as varreduras. **Antes de cada
mockup**, uma tarefa só de leitura escreve o seu arquivo — **um por seção**, para as quatro conferências andarem em
paralelo sem dividir arquivo:

| Arquivo | Tarefa | Linhas de chave |
|---|---|---|
| `docs/mockups/M2.3/conferencia-casco.md` | T2 | 2 |
| `docs/mockups/M2.3/conferencia-comportamento.md` | T5 | 22 |
| `docs/mockups/M2.3/conferencia-risco.md` | T8 | 9 |
| `docs/mockups/M2.3/conferencia-fundamentos.md` | T11 | 22 |

Cada um com ao menos uma linha por chave — **uma linha por (chave, ramo) é permitida**, e a contagem é de chaves
distintas:

| Chave | Ramo | O que a frase avançada vai afirmar | Conferido em | Parâmetros lidos (janela, anualização, nível, casas) |
|---|---|---|---|---|

A coluna "Conferido em" traz um ou mais `caminho:linha`, com o caminho relativo à raiz do repositório. Os lugares de
procurar são os do RF-05 da spec. **Afirmação sem `caminho:linha` não vai ao mockup.** O mockup copia a afirmação; o
portão aprova o texto.

**O critério de cada conferência é um comando**, rodado na raiz do worktree (Git Bash), com `F` o arquivo da tarefa e
`N` a contagem da tabela acima:

```sh
F=docs/mockups/M2.3/conferencia-<secao>.md; N=<2, 22, 9 ou 22>   # os dois valores da tarefa
test "$(grep -oE '^\| `[^`]+`' "$F" | sort -u | wc -l)" -eq "$N" || { echo "chaves distintas: esperado $N"; exit 1; }
grep -oE '[A-Za-z0-9_./-]+\.(py|ts|tsx):[0-9]+' "$F" | sort -u | while IFS=: read -r arq lin; do
  test -f "$arq" || { echo "falta $arq"; exit 1; }
  test "$(wc -l < "$arq")" -ge "$lin" || { echo "$arq tem menos de $lin linhas"; exit 1; }
done
```

A linha de chave começa por `` | `chave` ``; linha de chave sem nenhum `caminho:linha` reprova pela revisão do mockup,
que abre cada referência.

### A revisão do mockup, antes de cada portão

Cada tarefa de mockup termina com **um revisor (agente `revisor`, sem o contexto da conversa)** que confere o mockup
contra a spec e contra o arquivo de conferência da seção: cada frase avançada igual à afirmação conferida, cada
`caminho:linha` aberto, os dois níveis e os dois temas presentes, nenhuma frase que sugira ação (a condição da D-153),
e o que o RF-06 recolhe. Achado grave volta ao mockup antes do portão.
