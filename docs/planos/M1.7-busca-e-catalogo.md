### Onde cada coisa roda

**O bloco é implementado num worktree** (`E:/Temp/Trilobit/varlab-wt/M1.7-busca-e-catalogo`), e o
`compose.yaml` monta o checkout principal, não o worktree (aprendizado "O worktree não é o que o contêiner
monta"). Toda suíte roda **do checkout principal** (`E:/Temp/Trilobit/varlab`), num contêiner avulso com o
worktree montado por cima. Abaixo, `WT=E:/Temp/Trilobit/varlab-wt/M1.7-busca-e-catalogo`.

| O quê | Comando (do checkout principal) |
|---|---|
| teste do backend | `MSYS_NO_PATHCONV=1 docker compose run --rm --no-deps -v "$WT/backend:/repo/backend" worker python -m pytest <caminhos>` |
| `mypy` e `ruff` | o mesmo contêiner com `sh -c "mypy . && ruff check . && ruff format --check ."` |
| esquema OpenAPI (V-05) | o mesmo contêiner com `python manage.py spectacular --validate --fail-on-warn --file /tmp/schema.yaml` |
| frontend | `MSYS_NO_PATHCONV=1 docker compose run --rm --no-deps -v "$WT/frontend:/repo/frontend" -v "$WT/brand/ruvor:/repo/brand/ruvor:ro" -v "$WT/docs/mockups:/repo/docs/mockups:ro" frontend sh -c "npm test && npm run lint && npm run typecheck && npm run build"` (o `docs/mockups` porque `tests/icones.test.ts:21` lê o kit) |
| o mockup | aberto do worktree por `file://` (usa `../../../brand/ruvor/`), ou servido por `python -m http.server` na raiz do worktree, numa porta conferida livre antes (nunca matar processo por porta — memória da máquina) |

**Uma suíte de backend por vez**: o contêiner avulso usa o mesmo banco de teste do serviço, e outro agente
trabalha no `worker` desta máquina (o ramo `marco1/M2.1m-requested-by`). Antes de rodar a suíte, combinar com o
orquestrador; nunca `docker compose restart` nem `stop` em serviço.

### O stack servindo o ramo

Regra comum da frente. `git switch marco1/M1.7-busca-e-catalogo` no checkout principal é **recusado**: o ramo
está em uso pelo worktree. Quando uma tarefa precisa do stack servindo este ramo (a conferência visual da T6, a
T8), **o orquestrador** — não o implementador — confirma que ninguém usa o checkout principal, põe-no em `git
switch --detach <HEAD do ramo>`, e **o volta ao ramo de antes no fim**. Os commits continuam no worktree. Se a
`main` tiver avançado, ela entra no ramo (merge, no worktree) **antes** da T8. **Todo commit novo no worktree
pede um novo destaque**: o checkout principal destacado num HEAD velho serve o código velho — em particular o
`capturas.mjs` que a T8 altera é commitado no worktree **antes** de rodar, e o orquestrador destaca de novo o
checkout principal no HEAD novo (ou o `docker run` do Playwright monta `$WT/frontend/e2e` no lugar do
`frontend/e2e` do principal).

Em `search_assets`, só as duas condições de nome mudam: `Q(name__unaccent__icontains=q) |

### A anotação `has_risk` (RF-03) — literal, a falha é silenciosa

Em `backend/apps/api/views.py`, ao lado de `_with_has_prices`, e aplicada na busca junto com ela:

```python
def _with_has_risk(assets: QuerySet[Asset]) -> QuerySet[Asset]:
    """RF-03 do M1.7: a execucao fechada mais recente (o `latest` do `/risk`) e `ok` ou `partial`."""
    latest_closed_status = Subquery(
        RiskRun.objects.filter(asset=OuterRef("pk"), status__in=CLOSED_RUN_STATUSES)
        .order_by("-calculated_at")
        .values("status")[:1]
    )
    return assets.annotate(latest_closed_status=latest_closed_status).annotate(
        has_risk=Case(
            When(
                latest_closed_status__in=(RiskRun.Status.OK, RiskRun.Status.PARTIAL),
                then=Value(True),
            ),
            default=Value(False),
            output_field=BooleanField(),
        )
    )
```

`Subquery` e `BooleanField` entram no import de `django.db.models`. O nome da anotação auxiliar
(`latest_closed_status`) não sai na resposta: o serializador lista os campos. **O contrato é este**: o filtro de status fechado **antes** da ordenação, a mesma ordenação do `latest`, e a
comparação com `ok`/`partial` **depois** de escolher a mais recente. `CLOSED_RUN_STATUSES` sobe para antes da
função (hoje está na l.455). O filtro `has_risk=true|false` da busca filtra pela anotação.

### A tabela de correção (RF-07) — literal, é o contrato

`backend/apps/assets/classification.py`, só biblioteca padrão:

```python
"""A classificacao da B3 como a API a mostra (M1.7, RF-07; D-144).

O `silver` guarda o texto como a B3 o entrega, com ponto no lugar da virgula (D-47). A API
troca o texto inteiro pelo desta tabela; nunca substitui trecho. Texto novo com ponto, fora
das duas listas, aparece no relatorio do `import_assets` (RF-09).
"""

from collections.abc import Iterable

CORRECTED: dict[str, str] = {
    "Exploração. Refino e Distribuição": "Exploração, Refino e Distribuição",
    "Motores . Compressores e Outros": "Motores, Compressores e Outros",
    "Petróleo. Gás e Biocombustíveis": "Petróleo, Gás e Biocombustíveis",
    "Serv.Méd.Hospit..Análises e Diagnósticos": "Serv.Méd.Hospit., Análises e Diagnósticos",
    "Tecidos. Vestuário e Calçados": "Tecidos, Vestuário e Calçados",
}

# O ponto e abreviacao: ficam como vieram.
KEPT: frozenset[str] = frozenset(
    {
        "Máq. e Equip. Construção e Agrícolas",
        "Máq. e Equip. Industriais",
    }
)


def display_classification(text: str | None) -> str | None:
    if text is None:
        return None
    return CORRECTED.get(text, text)


def unknown_dotted(texts: Iterable[str | None]) -> list[str]:
    """Os textos com ponto fora das duas listas, distintos e em ordem alfabetica (RF-09)."""
    return sorted(
        {t for t in texts if t is not None and "." in t and t not in CORRECTED and t not in KEPT}
    )
```

### A linha do relatório (RF-09) — literal

`ImportReport` ganha `dotted_outside_table: tuple[str, ...] = ()` (com padrão, para as construções existentes
do dataclass não quebrarem), preenchido com `tuple(unknown_dotted(...))` sobre os `sector`,
`subsector` e `segment` do catálogo conformado nesta coleta. O `render()` acrescenta, depois da linha dos casos
de borda:

```
classificacao com ponto fora da tabela: {len(self.dotted_outside_table)}
```

e, só quando há algum, uma sexta linha: `  {"; ".join(self.dotted_outside_table)}`.

### A sugestão (RF-10 a RF-13)

- **Só o `SearchBox` de `variant === "page"` pede e guarda a sugestão**; o de `variant === "bar"` — que o
  `Shell.tsx:91-96` monta em **toda** rota fora de `/`, inclusive a tela do ativo — **não pede nada**. O de página
  pede `GET /api/v1/assets?has_risk=true&limit=8` **uma vez, num efeito de montagem**, e guarda o resultado num
  estado `suggestion: Load<AssetPage>` (`loading` / `ok` / `error`). `Suggestions` recebe o estado por prop e não
  pede nada.
- **O descarte da resposta atrasada** segue o molde do M1.6b (sequência). O `StrictMode` monta, desmonta e monta
  de novo em desenvolvimento, e por isso há dois pedidos: o do primeiro efeito tem de ser descartado. **O cenário
  do teste é fixo**: render dentro de `<StrictMode>`; o primeiro pedido fica pendente; o segundo responde A; o
  primeiro resolve depois — uma vez com erro, outra com B —; a tela continua em A. A mutação "sem descartar a
  resposta atrasada" deixa a tela em erro ou em B e reprova.
- `count > 8` → os oito e a frase "e mais N" (N = `count − 8`), sem link. `count == 0` → o estado "nenhum
  ativo com risco" do mockup. Erro → o estado de erro do mockup, **sem** botão que bloqueie a caixa.
- Os tipos (RF-05): `AssetBase` (os campos comuns de hoje, sem `has_risk`), `AssetItem = AssetBase & {
  has_risk: boolean }`, `AssetDetail = AssetBase & {...}`.
