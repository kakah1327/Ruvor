## Como ler este plano

[PROCESSO §5](../PROCESSO.md#5-anatomia-de-um-plano): **contratos, não corpos.** Literal onde o conteúdo
*é* o contrato — a configuração do proxy, a classe de permissão, as assinaturas do cliente e da sessão, a
função do `next` — e onde a falha é silenciosa — a repetição do CSRF com limite, a validação do `next`, a
troca obrigatória que não pode sair da URL, o foco devolvido pelo diálogo. Toda tarefa visual vira duas
(PROCESSO §7): o mockup, com o portão humano, e depois a implementação contra ele.

**Toda linha de critério de aceite começa por uma guarda** que prova que o contêiner vê o código do ramo —

## O que este plano decide

### O proxy (RF-19)

`frontend/vite.config.ts`, as duas entradas, literal:

```ts
proxy: {
  "/health": { target: proxyTarget, changeOrigin: false },
  "/api": { target: proxyTarget, changeOrigin: false },
},
```

Com um comentário de duas linhas acima: a forma curta liga o `changeOrigin`, e a checagem de origem do
CSRF do Django (D-100) passa a comparar `Origin: localhost:<porta>` com `Host: web:8000` e recusa.

### A permissão do `POST /risk` (RF-01)

`backend/apps/api/permissions.py`, novo, literal no essencial:

```python
from rest_framework.permissions import SAFE_METHODS, BasePermission

from apps.accounts.permissions import AccountReady


class ReadOpenWriteAccountReady(BasePermission):
    """Leitura aberta; escrita so com conta pronta (D-140).

    Metodo seguro -> True. Qualquer outro -> `AccountReady`: False sem login (o DRF responde
    401 `not_authenticated`), `password_change_required` com a senha provisoria por trocar.
    """

    def has_permission(self, request, view):
        if request.method in SAFE_METHODS:
            return True
        return AccountReady().has_permission(request, view)
```

(com as anotações de tipo que o `mypy` estrito pedir). `AssetRiskView` declara
`permission_classes = [ReadOpenWriteAccountReady]` no próprio corpo, e o `@extend_schema` do `post` passa a
`responses={202: AssetRiskOut, 401: OpenApiResponse(ApiErrorSerializer, description=…),
403: OpenApiResponse(ApiErrorSerializer, description=…)}`, com o `ApiErrorSerializer` de
`apps/accounts/schema.py`.

### O cliente HTTP (RF-02)

`frontend/src/api/client.ts`, a superfície:

```ts
export class ApiError extends Error { status; code; details }          // como hoje
export function apiGet<T>(path: string): Promise<T>;                  // como hoje
export function apiPost<T>(path: string, body?: unknown): Promise<T>; // body opcional: as chamadas de hoje não mudam
export function apiPatch<T>(path: string, body: unknown): Promise<T>;
export function apiDelete<T = undefined>(path: string): Promise<T>;
```

- **`headers` é sempre um objeto simples** (`Record<string, string>`), nunca `Headers` — os testes o leem
  por chave;
- com `body`, `Content-Type: application/json` e `JSON.stringify(body)`;
- **204 → `undefined`** (sem ler o corpo); 2xx com corpo não JSON → `unexpected_response`, como hoje;
- **método diferente de `GET`**: antes do pedido, se não há cookie `csrftoken`, um `GET /api/v1/auth/csrf`;
  **se esse `GET` falha, o cliente propaga o erro dele** (`ApiError` do `auth/csrf`) **e não faz o pedido**;
  o `X-CSRFToken` sai do cookie lido **depois** do `auth/csrf`, na hora; se a resposta é **403
  `csrf_failed`**, um `auth/csrf` e **uma** repetição — na segunda falha, o erro sobe. A repetição é um
  parâmetro interno (`retried: boolean`), nunca um laço.

### A sessão (RF-03)

`frontend/src/session/` (novo), a superfície:

```ts
// types.ts — os corpos do M2.1a (services.me_body e user_body)
export type Me = { email: string; name: string; role: "admin" | "member";
  must_change_password: boolean; is_staff: boolean;
  organization: { name: string; slug: string; is_personal: boolean } };
export type OrgUser = { email: string; name: string; role: "admin" | "member"; is_active: boolean;
  must_change_password: boolean; created_at: string; last_login: string | null };
export function isMe(value: unknown): value is Me;   // confere a forma: as chaves e os tipos acima

// SessionProvider.tsx
export type Session =
  | { status: "loading" }
  | { status: "anonymous"; ended: boolean }   // ended: 401 depois de estar logado (RF-16)
  | { status: "authenticated"; me: Me };
export type SessionApi = Session & {
  setMe(me: Me): void;          // login e signup (a resposta é o `me`)
  reload(): Promise<void>;      // relê auth/me — password, rebaixar a si mesma, password_change_required
  signOut(): Promise<void>;     // POST auth/logout; 204 ou 401 -> anônimo, sem erro
  expired(): void;              // 401 de rota que exige conta -> { anonymous, ended: true }
};
export function SessionProvider(props: { children?: ReactNode }): JSX.Element; // sem children: <Outlet/>
export function useSession(): SessionApi;   // fora do provedor: { status: "anonymous", ended: false } e ações inertes

// next.ts
export function safeNext(next: string | null, origin?: string): string;
export function signInHref(pathAndSearch: string): string;
// "/entrar?next=" + encodeURIComponent(pathAndSearch) — todo link para a entrada passa por ela
```

- **Onde mora** (RF-03): `routes` ganha uma rota de layout na raiz, `{ element: <SessionProvider />,
  children: [ <as telas fora do casco>, { element: <Shell />, children: [...] } ] }`;
- ao montar, **um** `apiGet("/api/v1/auth/me")`: 200 **com a forma de `Me`** (`isMe`) → `authenticated`;
  200 com outra forma, ou **qualquer erro** → `anonymous` com `ended: false`;
- **o bloqueio do RF-05** mora no `SessionProvider`: com `me.must_change_password`, ele renderiza a tela de
  troca obrigatória **no lugar do `<Outlet>`**, sem navegar — **exceto em `/entrar` e `/cadastro`**, que
  continuam montando a tela deles: a entrada bem-sucedida navega a `X` (o `next`), e `X` mostra a troca.

`safeNext`, literal no essencial:

```ts
export function safeNext(next: string | null, origin = window.location.origin): string {
  if (!next) return "/";
  let u: URL;
  try { u = new URL(next, origin); } catch { return "/"; }
  if (u.origin !== origin) return "/";
  if (u.pathname === "/entrar" || u.pathname === "/cadastro") return "/";
  return u.pathname + u.search;
}
```

```
T1 (proxy) ─────────┐
T2 (permissão) ─────┤
T3 (cliente) ─ T4 (sessão) ─┐
T5 (✋ entrada) ─ T6 (✋ cadastro) ─┐
```

revisado vai ao humano.

## Desvios do inventário da spec

- **`frontend/src/session/`** é diretório novo, fora dos que o inventário da spec nomeia (`screens/`,
  `components/`, `content/`, `api/`): a spec deixou o arquivo do estado de sessão ao plano ("o plano escolhe
  o arquivo"), e separar a lógica da sessão e do `next` de `components/` permite testá-la sem tela.
- **`frontend/src/session/types.ts`** guarda os tipos `Me` e `OrgUser`, que o inventário da spec punha em
  `frontend/src/api/types.ts`: eles são do contrato das rotas de conta, que só a sessão e as telas de acesso
  consomem, e ficam junto do `isMe` que confere a forma. `api/types.ts` não muda.
- **`backend/tests/api/test_pedido_conta.py`** é o "teste novo em `backend/tests/api/`" do RF-01 da spec, com
  nome.
- **`backend/tests/api/confere_esquema_risco.py`** é um script (não um teste coletado) que a T2 chama para
  conferir o 401 e o 403 no esquema gerado, fora do `sh -c`.
- **`frontend/tests/proxy.test.ts`**, `sessao.test.tsx`, `next.test.ts`, `entrada.test.tsx`,
  `cadastro.test.tsx`, `senha.test.tsx`, `conta.test.tsx`, `usuarios.test.tsx` e o módulo `dubles.ts` são os
  "testes em `frontend/tests/`" do inventário, com nome.
- **`frontend/e2e/acesso.mjs`** é o "roteiro em `frontend/e2e/`" do RF-20, com nome; o `capturas.mjs`
  continua separado e ganha a chave `RUVOR_E2E_SO_CONTA`.
- **A extensão da cerca de `docs/mockups/`** em `docs/FRENTES.md`, que a spec punha no FECHA, já entrou pela
  PR #22 (M2.3): a T5 só confere, e este bloco não mexe na linha.
- **Os mockups aprovados não são reescritos com as classes do kit** (a T5 do M1.6b os reescrevia): a
  correspondência se prova pela comparação da T16, por critério executável.
- **`README.md`** entra no FECHA (a spec o deixa implícito em "os documentos do FECHA"), como nos blocos
  anteriores.
