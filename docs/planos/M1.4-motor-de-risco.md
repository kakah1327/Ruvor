[PROCESSO §5](../PROCESSO.md#5-anatomia-de-um-plano): **contratos, não corpos.** Literal só
onde o conteúdo *é* o contrato (`db_table`, restrições, assinaturas, o bloco TOML da isenção)
ou onde a falha é silenciosa (o ponto de semeadura, o piso de 503, o veredito).

### Onde cada coisa roda — e isto muda no meio do bloco

| Antes da T1 | Depois da T1 |
|---|---|
| `docker compose exec -T web python -m pytest` | `docker compose exec -T worker python -m pytest` |
| `… web python -m mypy .` | `… worker python -m mypy .` |
| `… web ruff check .` | `… worker ruff check .` |

**Toda tarefa que produz código Python fecha com os três**, cada um com seu próprio
`docker compose exec` — `&&` encadeado roda a segunda metade no hospedeiro.

**O `mypy` do motor roda de dentro de `engine/`.** Da raiz ele não lê o
`engine/pyproject.toml` e produz ~37 erros que **já existem hoje** — `import-untyped` de
pandas/scipy/tensorflow e os dois módulos que a `ignore_errors` da D-21 cobre. É a forma
que a CI usa, e a configuração já traz `files = ["src"]`. Medido na T2.

As tarefas do motor (T2 a T5) rodam a suíte do motor **no `.venv/` nativo do hospedeiro**,
que é onde o motor vive ([CLAUDE.md](../../CLAUDE.md)), e é obrigatório para o V-05: a linha
de base **não é portátil**, e no Linux 8 dos 64 testes reprovam por dívida já aceita.

## O que este plano decide

### A semeadura — `engine/src/engine/seeding.py`

```python
DEFAULT_SEED = 42          # o padrao do motor; o do backend (config.DEFAULT_SEED) pode divergir

def configure(seed: int) -> None: ...    # guarda no modulo; chamado pelo runner
def apply() -> None: ...                 # semeia com o configurado, ou com DEFAULT_SEED
```

**`apply()` nunca é inerte.** Sem `configure()` prévio, semeia com `DEFAULT_SEED` — é o caso
do V-03, que roda sem `runner`. Se fosse inerte, o critério central do bloco mediria código
não semeado.

**O `import tensorflow` fica dentro de `apply()`**, nunca no topo do módulo: `runner.py`
importa `seeding`, e o `ruvor run` importa `runner` — um import de módulo tornaria o
TensorFlow obrigatório para o motor inteiro, e `engine[traditional,garch]` deixaria de
importar o runner.

`apply()` usa `keras.utils.set_random_seed`, que semeia `random`, o gerador **global legado**
do NumPy e o TensorFlow de uma vez. Os seis não neurais usam `np.random.default_rng(...)`,
que **não lê** esse estado — por isso o V-05 continua de pé.

### O `runner` — três acréscimos, nenhum cálculo alterado

```python
@dataclass
class ExperimentConfig:
    ...                          # campos atuais, intocados
    seed: int = seeding.DEFAULT_SEED

@dataclass
class ModelRunResult:
    ...                          # campos atuais, intocados
    estimate: VaREstimate | None = None

def run_experiment(config, provider) -> ExperimentResult:
    seeding.configure(config.seed)     # PRIMEIRA linha; configura, NAO semeia
    ...
```

O `estimate` é preenchido onde hoje a `VaREstimate` é descartada. **Nenhuma linha de cálculo
muda de lugar**, e o V-05b prova comparando com a chamada direta no mesmo processo.

### `VaRModel.hyperparameters` — a lista fechada

Propriedade de leitura em `models/base.py`, `{}` por padrão, sobrescrita em **seis** arquivos.
**A fronteira é comportamento, não arquivo**: os quatro não neurais que a declaram são
editados, e o que não pode mudar é o que eles calculam.

| Arquivo | Declara |
|---|---|
| `models/base.py` | a propriedade, devolvendo `{}` |
| `models/ml/_quantile_nn.py` | `window`, `refit_frequency_days`, `grid`, `learning_rate`, `batch_size`, `search_epochs`, `refit_epochs`, `patience`, `val_fraction` — herdado pelos três neurais |
| `models/traditional/monte_carlo.py` | `n_simulations`, `random_state` |
| `models/garch/_conditional.py` | `dist`, `refit_frequency_days` |
| `models/garch/garch_1_1.py`, `egarch.py` | o do pai mais o `_arch_kwargs()` de cada um |
| `models/ml/caviar.py` | `refit_frequency_days`, `n_restarts` — **constantes de módulo**, escritas literalmente, com comentário dizendo por quê |

`parametric` e `historical` **não são tocados**: herdam o `{}`.

### De onde vem cada valor gravado

O `ExperimentResult` expõe pouco: `config`, e por `ModelRunResult` o `model_name`, o `alpha`,
os `backtests`, o `error` e — pela alteração 3 — a `estimate`. **Todo o resto o `compute.py`
monta por fora**, e sem esta tabela cada implementador monta de um jeito.

| Coluna | Origem |
|---|---|
| `asset`, `calculated_at`, `seed`, `train_window_days` | o que `run_compute_risk` recebeu; `calculated_at` é `now()` **uma vez por execução** |
| `engine_version` | `importlib.metadata.version("ruvor-engine")` — lê a metadata **instalada**, então o bump da T2 só chega ao `worker` com `--build`, que a T5 faz. O V-14 confere que vale **`0.2.0`**, não só que é não nulo |
| `finished_at` | `now()` ao fim do ativo |
| `first_price_date`, `as_of_date`, `price_count` | a **série que o motor viu**, isto é, depois do `clean_prices` — a mesma sobre a qual o piso é medido |
| `train_count`, `test_count` | `train_window_days` e `len(retornos) − train_window_days` |
| `requested_by` | **sempre nulo** — não há usuário autenticado antes do M2.1, e a spec declara a D-15 cumprida pela metade. Está aqui porque a tabela existe para não deixar coluna sem origem, e "nulo por decisão" é uma origem |
| `price_run` | **o maior `run_id` entre as linhas de `silver.price` usadas** — não o `run` da linha de maior data; a spec explica por quê, e são números diferentes |
| `model_name`, `alpha`, `error` | do `ModelRunResult` |
| `model_category` | `get_model(model_name).category.value` |
| `hyperparameters` | `get_model(model_name)().hyperparameters` — ver abaixo |
| `var_latest`, `var_mean` | `run.estimate.var_series.iloc[-1]` e `.mean()` |
| `violations`, `expected_violations` | `details` do **Kupiec**, não da Basileia — janelas diferentes |
| `*_passed`, `*_p_value` | dos quatro `BacktestResult`, por `test_name` |
| `basel_zone` | `details["zone"]` da Basileia |
| `adequate` | o veredito literal |

**`price_count` é medido depois do `clean_prices`, junto com o piso.** Na prática as duas
contagens coincidem, porque o M1.2 já descarta barra com `close` ou `adj_close` nulo — mas
medir as duas coisas sobre a mesma série elimina a divergência por construção, em vez de
deixá-la latente.

**O `hyperparameters` vem de uma instância nova, criada fora do `runner`.** É leitura pura,
não depende de estado de ajuste, e todos os nove construtores têm padrão para tudo — então
`get_model(nome)()` funciona para os nove. **A rota alternativa é proibida:** acrescentar
`hyperparameters` ao `ModelRunResult` seria uma **quinta** alteração no motor, além das quatro
que o [RF-02](../specs/M1.4-motor-de-risco.md#rf-02) autoriza, e o motor está congelado pela
[D-21](../decisoes/D-21-motor-ml-congelado-ate-etapa-6.md). Dito porque é a rota que ocorre
primeiro a quem estiver com o `runner` aberto.

### As datas que o motor pede

`ExperimentConfig` exige `start` e `end` como **`str`**, e o contrato do provedor é
`fetch(ticker, start: str, end: str)`. O `compute.py` passa a janela inteira da série do
ativo em ISO (`YYYY-MM-DD`), e **o provedor filtra por ela** — não a ignora.

Filtrar importa mesmo quando o `compute.py` passa a janela inteira: é o que mantém o
`SilverPriceProvider` um `DataProvider` honesto, utilizável por quem pedir outro intervalo, em
vez de um objeto que só funciona para este chamador.

### O que a T6 decidiu, e que a T7 herda

Cinco bordas que nem a spec nem o plano fixavam, resolvidas na costura e medidas ali:

- **O intervalo do provedor é fechado dos dois lados** (`date__lte=end`). O `YFinanceProvider`
  do motor delega ao `yf.download`, cujo `end` é **exclusivo** — e um `end` exclusivo engoliria
  o último pregão, fazendo `as_of_date` sair errado. A T7 passa a janela assumindo **inclusivo**.
- **Série vazia devolve `DataFrame` vazio**, não levanta. Quem decide o que fazer com ativo
  sem preço é o `compute.py`, pelo piso `MIN_SESSIONS` — não o provedor.
- **O `adj_close` vai para `float`, e isso é obrigatório, não estético.** `Decimal` na coluna
  produz `dtype=object` e o `np.log` do `log_returns` quebra.
- **A varredura do V-08 é textual** sobre todos os `*.py` de `apps/risk/`, procurando
  `YFinanceProvider` **e** `yfinance`. Consequência: **nenhum arquivo de `apps/risk/` pode
  mencionar a palavra**, nem em comentário ou docstring. É deliberado — critério mais estrito
  é critério mais honesto.
- **O `ruff` trata `engine` como import de terceiros**, junto de `numpy` e `pandas`, antes dos
  `apps.*`. Contraria a intuição de "motor do monorepo é first-party"; é só ordenação.

### `alpha`: float no motor, `Decimal` na coluna

`ExperimentConfig.alphas` é `list[float]`, e o caminho de cálculo usa o valor como float em
`-norm.ppf(alpha)`, `np.quantile(..., alpha)`, na perda pinball e **como chave de cache** do
`_quantile_nn`. Passar `Decimal` quebra.

```python
ALPHAS = (0.05, 0.01)                                   # float, e o motor recebe assim
alpha_col = Decimal(str(run.alpha)).quantize(Q4)        # Decimal(6,4) na volta
```

É a única constante do bloco que atravessa a fronteira motor↔banco, e a conversão vai nos
dois sentidos escrita porque `Decimal(0.05)` — sem o `str` — não é `0.0500`.

### Carregar o registry antes de consultá-lo

`list_models()` lê um dicionário que só é populado por `load_all_model_modules()`; o mesmo
vale para os backtests, que o `run_experiment` consulta por `get_backtest`. O `cli.py` chama
as duas antes de montar o `ExperimentConfig`, e o teste da linha de base também.

```python
load_all_model_modules()
load_all_backtest_modules()
faltando = [m for m in pedidos if m not in list_models()]
if faltando:
    raise ModelsMissing(faltando)
```

Sem as duas primeiras linhas, **toda execução levanta `ModelsMissing` com os nove**. Falha
alto, então não passa despercebido — mas é retrabalho garantido num trecho que este plano
escolheu fixar ao pé da letra.

**A lista dos nove mora em `MODELS`, constante de módulo em `apps/risk/compute.py`** — não em
`config.py`, cujo conteúdo este plano fixou literalmente e sem ela. E **não pode ser
`list_models()`**: o padrão compararía o registry consigo mesmo, o `faltando` sairia sempre
vazio e **a denúncia do RF-17 nunca dispararia** — critério passando vazio. Um teste confere
`sorted(MODELS) == list_models()` num ambiente completo, para a lista não envelhecer calada.

## Ordem e dependências

```
T1 (suite no worker)  ──┬──────────────────────────────┐
T2 (semente) ── T3 (runner) ── T4 (hyperparams) ── T5 (app+tabelas) ── T6 (provider) ── T7 (compute) ── T8 (casca) ── T9 (mutacoes) ── T10 (execucao real + FECHA)
```

**A T1 vem primeiro e sozinha.** Sem ela, nenhuma tarefa de backend que importe o motor tem
onde ser verificada — `apps/risk/provider.py` não compila sob o `mypy` da `web`, que não tem
o motor. T2, T3 e T4 são do motor e não dependem dela — poderiam correr em paralelo com a T1, que só
toca backend e infraestrutura. A sequência única é escolha de prudência num bloco que altera
o ativo científico do projeto, não necessidade técnica: **a única dependência real é T5 → T1**,
porque sem a suíte no `worker` nada que importe o motor tem onde ser verificado.

**Nada é paralelizado neste bloco.** T2→T3→T4 escrevem no mesmo pacote do motor; T5→T7 no
mesmo app.

### Tarefa 1 — A suíte e o `mypy` migram para o `worker`

**Depende de:** nada · **Visual:** não

**Arquivos**
- altera: `compose.yaml`, `.github/workflows/ci.yml`, `README.md`, `backend/pyproject.toml`

**Contrato**
- `compose.yaml`: o `worker` ganha `depends_on` do `postgres`, com `condition:
  service_healthy`, ao lado do `redis` que já tem. **Sem isso a suíte migrada não tem banco.**
- `ci.yml`, trabalho `backend`: `web` → `worker` nos quatro comandos, e
  `timeout-minutes: 20` → **30**, o mesmo do trabalho `motor`, cujo comentário já diz que ele
  "baixa TensorFlow e tem folga maior".
- **O teto do trabalho `motor` é reexaminado pela T3, não aqui.** Ele passa a rodar, além dos
  64 testes atuais, o V-03 e o V-05b. A medição e a eventual mudança estão no critério da T3,
  que é quem fecha o trabalho no motor — **instrução que mora na tarefa errada é instrução que
  ninguém executa**, e `ci.yml` não pode ter dois donos. Esta tarefa mexe só no teto do
  `backend`.
- `README.md`: **só as linhas de `pytest` e `mypy`** trocam de contêiner na tabela de
  comandos — é o que o RF-16b manda. `migrate`, `import_assets`, `import_prices` e
  `compute_metrics` **continuam no `web`**: eles não importam o motor, e movê-los seria
  escopo que ninguém pediu.

  **A seção de CI do mesmo arquivo também muda**, e não é exceção à regra acima: ela
  *descreve* o `ci.yml`, que esta tarefa altera. Duas afirmações ficam falsas — o contêiner
  do trabalho `backend`, e a frase "nenhum trabalho constrói a `worker`". Deixá-las intactas
  produziria documentação mentirosa, que é o oposto do que a cerca protege.
- `backend/pyproject.toml`: as duas isenções de tipagem, com os comentários **literais** da
  spec — `engine.*` com `ignore_errors`, `pandas.*` com `ignore_missing_imports`.

**`pandas` não entra em `dependencies`.** Ele chega pelo motor, instalado só no `worker`.
Declará-lo instalaria na `web`, que é o que a decisão sobre as imagens recusou.

**Critério de aceite**
```
docker compose up -d --build --wait worker          # sobe o postgres junto
docker compose exec -T worker python manage.py migrate
docker compose exec -T worker python -m pytest      # os 200 do M1.3 seguem passando
docker compose exec -T worker python -m mypy .
docker compose exec -T worker ruff check .
docker compose exec -T worker ruff format --check .
```
Mais a prova de que a dependência do banco é necessária: com o `depends_on` removido,
