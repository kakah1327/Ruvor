## Como ler este plano

[PROCESSO §5](../PROCESSO.md#5-anatomia-de-um-plano): **contratos, não corpos.** Literal só
onde o conteúdo *é* o contrato (`db_table`, restrições, assinaturas de costura, constantes
numéricas) ou onde a falha é silenciosa (a fronteira da janela, o desempate do drawdown, o
acessor do benchmark, o descarte de nulo).

O padrão a imitar já existe no repositório e **este plano cita em vez de repetir**:

| Para | Copiar de |
|---|---|
| módulo de cálculo puro, sem modelo nem transação | `apps/assets/conform_prices.py` |
| laço por ativo, transação, relatório, exceções | `apps/assets/prices.py` |
| casca de linha de comando | `apps/assets/management/commands/import_prices.py` |
| app, `apps.py`, `db_table` com esquema | `apps/assets/` |

Todo critério roda **no contêiner `web`**
([D-33](../decisoes/D-33-dia-a-dia-dentro-do-conteiner.md)):
`docker compose exec -T web python -m pytest …`.

**Toda tarefa que produz código Python fecha com estes três**, e eles não se repetem no corpo
de cada tarefa:

```
docker compose exec -T web python -m mypy .
docker compose exec -T web ruff check .
docker compose exec -T web ruff format --check .
```

Cada `&&` precisa do seu próprio `docker compose exec`: `… exec -T web ruff check . && ruff
format --check .` roda a segunda metade **no hospedeiro**, onde o `ruff` não está no `PATH` e
o diretório de trabalho é a raiz, não `backend/`. O `ruff` é o que pega o `F401` que a T2
pode deixar para trás, e a CI o roda a cada push
([D-43](../decisoes/D-43-ruff-e-biome-e-onde-cada-verificacao-roda.md)) — com commit direto
na `main`, lint quebrado aterrissa.

### Tipos de entrada e saída do cálculo puro

`metrics.py` **não importa modelo**, pelo mesmo corte que `conform_prices.py` faz. Recebe
dataclasses próprias; quem lê o banco e converte é `compute.py`.

Duas notas de tradução, que é onde `compute.py` pode errar em silêncio:

- **`Bar` aqui não é o `Bar` de `conform_prices.py`.** Nome igual, campos diferentes, módulos
  distintos — sem dano, mas não os confunda ao copiar o molde.
- **`CorporateEvent.amount` é `null=True` no modelo.** Dividendo com `amount` nulo é
  descartado ao montar a lista, e não entra em `dividend_payments_12m`: pagamento sem valor
  não é pagamento que se possa somar.

```python
@dataclass(frozen=True)
class Bar:
    date: date
    close: Decimal
    adj_close: Decimal
    volume: int
    log_return: Decimal | None

@dataclass(frozen=True)
class Dividend:
    date: date
    amount: Decimal          # nao anulavel: quem monta a lista filtra amount IS NULL

@dataclass(frozen=True)
class Drawdown:
    depth: Decimal
    peak_date: date
    trough_date: date
    recovery_date: date | None
    recovery_sessions: int | None

@dataclass(frozen=True)
class HistogramBin:
    index: int                 # 0..41
    lower: Decimal | None      # None so no indice 0
    upper: Decimal | None      # None so no indice 41
    count: int

@dataclass(frozen=True)
class Metrics:
    as_of_date: date
    first_price_date: date
    price_count: int
    returns: dict[str, Decimal | None]      # "1m".."120m" e "ytd"
    volatility: dict[str, Decimal | None]   # "12m", "60m"
    drawdown: Drawdown                      # nunca None: `bars` nunca chega vazio
    beta_60m: Decimal | None
    correlation_60m: Decimal | None
    benchmark_observations: int | None
    skewness: Decimal | None
    excess_kurtosis: Decimal | None
    statistical_observations: int | None
    dividends_12m: Decimal
    dividend_payments_12m: int
    dividend_yield_12m: Decimal
    avg_volume_21d: Decimal | None
    avg_volume_252d: Decimal | None
    histogram: list[HistogramBin]           # sempre 42, sempre em ordem de indice
```

`returns` e `volatility` são dicionários **de chave fechada**, e `compute.py` os desmonta em
colunas. É o que evita quinze parâmetros posicionais sem perder a tipagem da tabela larga.

### Assinaturas do cálculo puro

```python
def months_before(d: date, months: int) -> date
def window_bars(bars: list[Bar], months: int, as_of: date) -> list[Bar] | None
def ytd_bars(bars: list[Bar], as_of: date) -> list[Bar] | None
def window_returns(window: list[Bar]) -> list[Decimal]
def total_return(window: list[Bar]) -> Decimal
def annualized_volatility(returns: list[Decimal]) -> Decimal | None
def max_drawdown(bars: list[Bar]) -> Drawdown        # nunca None: ver abaixo
def skewness_and_kurtosis(returns: list[Decimal]) -> tuple[Decimal | None, Decimal | None]
def histogram(returns: list[Decimal]) -> list[HistogramBin]
def beta_and_correlation(
    asset_bars: list[Bar], benchmark_bars: list[Bar] | None, as_of: date
) -> tuple[Decimal | None, Decimal | None, int | None]
def dividend_summary(
    dividends: list[Dividend], as_of: date, as_of_close: Decimal
) -> tuple[Decimal, int, Decimal]
def average_volume(bars: list[Bar], sessions: int) -> Decimal | None
def compute(
    bars: list[Bar], dividends: list[Dividend], benchmark: list[Bar] | None
) -> Metrics
```

**`as_of` é parâmetro, não derivado dentro de cada função.** É `bars[-1].date`, calculado uma
vez em `compute` e passado adiante: derivar em cada função convida a divergência quando
alguém mudar a regra.

**`benchmark_bars` é `None` quando o índice não existe** (RF-16) **e quando o ativo é o
próprio Ibovespa** (RF-08). Os dois casos produzem a mesma tripla `(None, None, None)`, e
quem decide qual é qual é `compute.py`, não `metrics.py`.

**`beta_and_correlation` recebe as duas séries INTEIRAS e janela por dentro** — mas as duas
**não são simétricas**, e é aí que a observação se perde.

A janela de retornos é a do **ativo**; o benchmark é covariável, e entra por data. Tratar os
dois como espelhos produz erro dos dois lados: janelar o benchmark e aplicar-lhe
`window_returns` descartaria o `Q₀` dele e perderia um par legítimo; mas simplesmente
"janelar cada série e emparelhar" deixaria entrar o `log_return` de **`P₀` do ativo**, que a
spec exclui por medir movimento anterior à janela. As duas leituras gravam `beta_60m` e
`benchmark_observations` diferentes, e nenhum critério as distingue — o V-07 dá beta 2 com ou
sem o par extra, porque a relação é exata em todo par.

A regra, então, é assimétrica de propósito:

```python
# 1. datas elegiveis = as datas de retorno do ATIVO: P1..Pn da janela de 60m,
#    ja sem P0 (window_returns) e ja sem nulo.
# 2. o par entra quando o benchmark tem, NAQUELA data, log_return nao nulo.
#    Q0 do benchmark nao e descartado por ser Q0 -- so por ausencia ou nulo.
# 3. benchmark_observations = len(pares).
```

A etapa 1 **não chama `window_returns`**: ela precisa das datas, e `window_returns` devolve
`list[Decimal]` sem elas. `beta_and_correlation` itera `window[1:]` por conta própria, com o
mesmo critério. Mudar a assinatura de `window_returns` para devolver `Bar` quebraria o bloco
literal da T3 **e** a cerca da T4 ao mesmo tempo.

> É o mesmo erro que o bloco literal de `window_returns` existe para impedir, aparecendo do
> outro lado da função. **A mutação nº 6 da spec — "incluir o `log_return` do primeiro pregão
> da janela" — reprova em V-11b *e* em V-08b**, porque toca `statistical_observations` e
> `benchmark_observations`. A T7 precisa medir as duas.
>
> **E ela só morde se o cenário deixar.** A mutação troca `window[1:]` por `window[…]`, mas o
> filtro de nulo continua no lugar: se `P₀` for o **primeiro pregão da série** — que é como
> quase todo cenário curto nasce —, o `log_return` dele é nulo, nenhuma observação é
> acrescentada, e V-06, V-08b e V-11b **passam todos verdes**. O cenário de V-08b e V-11b
> precisa, portanto, de duas coisas: a série do ativo se estende **antes** do início da
> janela, para que `P₀` tenha `log_return` não nulo; e, para o V-08b, o benchmark negocia
> naquela data com `log_return` não nulo. Sem isso, a T7 reporta "mutação passou", o plano
> manda parar e escalar, e a volta é gasta descobrindo que o defeito estava no cenário da T4.

**Menos de 30 pares, com a janela existindo:** `beta_60m` e `correlation_60m` são nulos, e
`benchmark_observations` grava **a contagem real**, não nulo. O mínimo diz que o número não
merece confiança, não que ele seja desconhecido — e é a contagem que deixa isso auditável.
Nulo em `benchmark_observations` fica reservado aos dois casos de identidade e ausência
acima, mais a janela inexistente do V-09b.

### Orquestração — `apps/analytics/compute.py`

Sem `SOURCE` e sem `CollectionRun`: `gold.behavior_metric` **não** tem FK para coleta, e a
spec exclui manifesto do escopo. O molde tem uma constante dessas; copiá-la aqui convidaria a
T5 a criar uma execução em `bronze` que nenhuma tabela referencia e nenhum critério cobre.

```python
class InvalidTickers(Exception):      # propria de compute.py -- ver a nota sobre _resolve
    tickers: list[str]

class MetricsFailed(Exception):
    report: MetricsReport

@dataclass(frozen=True)
class AssetResult:
    ticker: str
    price_count: int
    as_of_date: date | None
    null_columns: list[str]
    error: str | None
    skipped: bool
    reason: str = ""          # "inativo" | "sem preco", so quando skipped
    def render(self) -> str: ...

@dataclass(frozen=True)
class MetricsReport:
    results: list[AssetResult]
    elapsed: float            # medido com time.monotonic(), so para exibir
    benchmark_missing: bool
    @property
    def failed(self) -> bool: ...
    def render(self) -> str: ...

def write_metrics(
    asset: Asset, calculated_at: datetime, metrics: Metrics

def run_compute_metrics(
    tickers: list[str], *, now: Callable[[], datetime] = timezone.now

```

**`write_metrics` é chamada pelo nome global dentro de `run_compute_metrics`**, como
`write_conformed` é em `prices.py`: é o que permite ao `monkeypatch` em
`apps.analytics.compute.write_metrics` provar a transação por ativo (V-12).

**A seleção de ativos é reescrita em `compute.py`, não importada.** A regra é a mesma do
`_resolve` de `prices.py` e o molde é ele, mas `_resolve` é **privado e de outro app**:
importá-lo acoplaria `analytics` à superfície interna de `assets` e faria a exceção levantada
ser `apps.assets.prices.InvalidTickers` — que o `except InvalidTickers` da T6, importando de
`compute`, **não pegaria**. `compute.py` tem a própria `InvalidTickers` e o próprio
`_resolve`. É duplicação deliberada de **vinte e quatro linhas** — `prices.py:170-193`,
contadas no arquivo — para não criar dependência entre apps.

A regra, então:

- **com tickers:** deduplica, ordena, e aborta com `InvalidTickers` se algum não existe ou
  não é `active` — antes de qualquer escrita;
- **sem tickers:** `Asset.objects.filter(prices__isnull=False).distinct().order_by("ticker")`,
  com os `inactive` pulados e os `active` processados.

**O ticker explícito sem preço é pulado, não é erro.** É o único caso em que ele aparece: com
tickers, `_resolve` **não filtra por preço** — devolve o ativo `active` sem nenhuma linha em
`silver.price` como processável. Sem este ramo, a T5 receberia `bars == []`, e `as_of =
bars[-1].date` levantaria `IndexError`. O contrato:

```python
# Antes de calcular: serie vazia e pulo, com motivo proprio. Nunca linha em gold com
# as_of_date nulo -- a coluna e NOT NULL, e "metrica de ativo sem preco" nao existe.
if not bars:
    results.append(AssetResult(asset.ticker, 0, None, [], None, skipped=True,
                               reason="sem preco"))
    continue
```

`AssetResult` ganha, portanto, um campo `reason: str` que distingue os dois pulos —
`"inativo"` e `"sem preco"` — e a `cauda` do relatório passa a ter cinco formas, não quatro.

**Formato do relatório**, literal — é contrato e o V-23 compara contra ele:

```python
# Linha por ativo -- reproduz o exemplo da spec byte a byte nos alinhamentos 12/8/14.
f"{r.ticker:<12}{r.price_count:>8} pregoes  {quando:<14}  {cauda}"
# quando = f"ate {r.as_of_date}" ou "-"
# cauda  = "ok"
#        | f"ok  (nulas: {', '.join(r.null_columns)})"
#        | f"pulado: {r.reason}"          # "inativo" | "sem preco"
#        | f"FALHOU ({r.error})"

# Aviso (so quando benchmark_missing), imediatamente antes do resumo:
#   "aviso: IBOV sem preco — beta e correlacao nulos em todos os ativos"

# Resumo -- os quatro contadores, com origem declarada:
total   = len(results)                                  # inclui os pulados
pulados = sum(1 for r in results if r.skipped)
falhos  = sum(1 for r in results if r.error)
ok      = total - pulados - falhos
f"metricas: {total} ativos, {ok} ok, {falhos} falhos, {pulados} pulados, {elapsed:.1f}s"
```

**`total` inclui os pulados, e isso diverge do molde de propósito.** `PricesReport.render()`
conta `len(asked)`, **sem** os pulados — `tests/assets/test_prices.py` fixa
`"coleta: 2 ativos, 2 ok, 0 falhos, 1 pulados"`, onde 2 + 1 = 3 ativos apareceram. O exemplo
da spec exige o contrário: `4 ativos, 3 ok, 0 falhos, 1 pulado`, com quatro linhas acima.
Quem copiar o molde sem ler isto escreve `3 ativos` e quebra o V-23.

O plural é invariável — `1 pulados`, como o `import_prices` já grava. O exemplo da spec foi
acertado para isso.

**Ramo vazio**, herdado do molde **com uma correção**: quando nenhum ativo é processável, o
relatório traz as linhas de pulo e depois `nenhum ativo ativo com preco; informe tickers`,
**sem** a linha `metricas:`. Essa mensagem só sai **quando nenhum ticker foi informado** —
mandar "informe tickers" a quem acabou de informar um (`compute_metrics XPTO9`, ativo `active`
sem preço) é o relatório mentindo, e é exatamente a saída que o caso de aceite novo da T5
compara. Com tickers informados e nada processável, saem só as linhas de pulo.

**Três pontos que o plano deixou em aberto e a T5 decidiu — congelados aqui:**

- **Ordem das linhas.** Os processados primeiro, em ordem de ticker; os pulados por
  `inativo` no fim. O molde faz o oposto (`prices.py` põe os pulados primeiro), mas o exemplo
  da spec traz `BAZZ4 … pulado: inativo` **depois** dos três calculados, e o exemplo é
  contrato. O pulo por `sem preco` acontece dentro do laço e fica na posição do ticker.
- **Como `render()` sabe se houve tickers.** `MetricsReport` tem três campos e nenhum diz
  isso, mas a mensagem `informe tickers` só pode sair quando não houve. É **derivado**: quem
  informou tickers só pode ter pulo por `sem preco` — o inativo explícito aborta antes, em
  `InvalidTickers` —, e quem não informou só pode ter pulo por `inativo`. A dedução depende
  de um invariante do `_resolve`, que mora no **mesmo arquivo**; se ele mudar, esta regra
  muda junto, e é isso que a torna aceitável em vez de frágil.
- **Colunas do ativo que FALHOU.** `price_count` e `as_of_date` trazem o que **foi lido**,
  não zero: a série foi lida, o que falhou foi o cálculo ou a gravação. A convenção
  `0 pregoes` e `-` é do **pulado**, onde nada chegou a ser considerado.

**`elapsed` é medido com `time.monotonic()` e só é exibido** — nenhuma lógica depende dele.
Para o V-23 ser determinístico, o teste constrói o `MetricsReport` diretamente com um
`elapsed` fixo e chama `render()`, em vez de cronometrar uma execução real.

### Tabela de colunas → chave em `Metrics`

O desmonte de `returns` e `volatility` em colunas é mecânico, e escrever a correspondência
aqui evita que a T5 a invente:

`return_1m` … `return_120m` ← `returns["1m"]` … `returns["120m"]` · `return_ytd` ←
`returns["ytd"]` · `volatility_12m`, `volatility_60m` ← `volatility["12m"]`,
`volatility["60m"]` · `max_drawdown*` ← campos de `drawdown`.

**`drawdown` nunca é `None`.** O guarda de `bars` vazio garante série não vazia, e sobre série
não vazia a maior queda sempre existe — nem que seja `0`, num ativo que só subiu. Por isso a
assinatura não leva `| None`: `max_drawdown`, `peak_date` e `trough_date` são **sempre**
preenchidos, e só as duas colunas de recuperação podem ser nulas. Ramo que nunca ocorre é
ramo sem teste, e alguém acaba preenchendo-o errado.

`null_columns` é a lista dos nomes de **coluna** que saíram nulos **por falta de histórico**,
na ordem da tabela da spec — não das chaves do dicionário, e **não** toda coluna nula.

O filtro é o que faz o exemplo da spec fechar, e sem ele o relatório mente em duas linhas:

| Nulo por | Entra em `null_columns`? |
|---|---|
| a janela não existe (`return_120m` num ativo de três anos) | **sim** — é o que o relatório existe para dizer |
| o ativo **é** o Ibovespa (`beta_60m`, `correlation_60m`, `benchmark_observations`) | **não** — é identidade, não lacuna; por isso a linha `IBOV … ok` do exemplo não traz `(nulas: …)` |
| o índice **falta** (RF-16) | **não** — tem linha de aviso própria, e repeti-la em todo ativo é ruído |
| a maior queda **não foi recuperada** (`max_drawdown_recovery_date`, `_sessions`) | **não** — nulo aqui é informação, e PETR4 real quase certamente cai neste caso |
| **menos de 30 pares** no emparelhamento, com a janela existindo (`beta_60m`, `correlation_60m`) | **sim** — é falta de histórico, só que do lado do índice; `benchmark_observations` fica preenchido e diz quantos pares houve |
