## Como ler este plano

[PROCESSO §5](../PROCESSO.md#5-anatomia-de-um-plano): **contratos, não corpos.** Entra literal só onde
o conteúdo é o contrato — a variável, a linha do `.env.example`, a corrente da rotina, os nomes de
tarefa — ou onde a falha é silenciosa: o `close_run` condicional, o bloco travado da tarefa por modelo,
o `on_commit` da abertura e **os dois testes de concorrência**, cuja ordem de threads é o que decide se
a mutação reprova.

## O que este plano decide

### Onde mora a varredura — `apps/risk/stale.py`, novo

A spec deixou a escolha ao plano. **Módulo novo**, `backend/apps/risk/stale.py`: a varredura não
calcula nada, e `compute.py` já carrega o laço, o manifesto e a escrita. `stale.py` importa de
`compute.py` (`close_run`, `count_results`) e de `apps.api.ondemand` (`lock_asset`, `close_linked`).
Não importa o motor diretamente, **mas o `compute.py` importa**: a varredura, a tarefa e o comando
`close_stale_runs` — inclusive o `--dry-run` — só rodam no `worker`, como o `compute_risk`.

### `close_run` condicional — literal, em `compute.py`

A contagem sai para uma função própria, que o `--dry-run` também usa; o ponto de desvio fica **entre a
contagem e o `UPDATE`** (é onde o V-08b para a varredura); a escrita é um `update` filtrado.

```python
def count_results(run: RiskRun) -> tuple[int, int, int]:
    """(esperados, gravados, com erro) da execucao, lidos do banco."""
    results = RiskResult.objects.filter(run=run)
    return (
        len(run.requested_models) * len(config.ALPHAS),
        results.count(),
        results.exclude(error="").count(),
    )


def _after_close_count() -> None:
    """Ponto de desvio dos testes concorrentes, entre a contagem do fecho e o `UPDATE`. Nao
    faz nada; e chamado pelo nome global deste modulo."""


def close_run(run: RiskRun, finished_at: datetime) -> str | None:
    """O fecho (RF-05 do M1.5; RF-08 do M1.5c): conta no banco, aplica a regra e escreve
    estado e fim **so se a linha ainda esta `running`** (D-150). Devolve o status escrito, ou
    `None` se a linha ja estava fechada; nos dois casos, o objeto fica com o que esta gravado."""
    status = status_for(*count_results(run))
    _after_close_count()
    updated = RiskRun.objects.filter(pk=run.pk, status=RiskRun.Status.RUNNING).update(
        status=status, finished_at=finished_at
    )
    run.refresh_from_db(fields=["status", "finished_at"])
    return status if updated else None
```

`status_for(expected, written, with_error)` não muda. Quem chama `close_run` e só segue com
`close_linked` quando ele devolve status: o fecho do `chord` (RF-09), a varredura (RF-02) e a abertura
que não enfileira (RF-11). **`close_linked` continua levantando sobre execução `running`** — é a guarda
de quem esquecer o retorno.

### A escrita travada da tarefa por modelo — literal, em `tasks.py`

```python
def _before_write_lock() -> None:
    """Ponto de desvio dos testes concorrentes, antes do bloco travado da escrita da tarefa
    por modelo. Nao faz nada; e chamado pelo nome global deste modulo."""


def _write_if_running(
    run_id: int, asset_id: int, model_name: str, write: Callable[[RiskRun], None]
) -> bool:
    """Grava sob a trava por ativo so se a execucao ainda esta `running` (RF-10, D-150).

    A releitura e **depois** da trava: e a trava dos dois lados -- aqui e no fecho -- que faz a
    contagem do fecho valer no instante do `UPDATE`. Fechada, descarta e devolve `False`.
    """
    _before_write_lock()
    with transaction.atomic():
        lock_asset(asset_id)
        run = RiskRun.objects.get(pk=run_id)
        if run.status != RiskRun.Status.RUNNING:
            logger.info("execucao %d fechada: modelo %s descartado", run_id, model_name)
            return False
        write(run)
    return True
```

Em `_compute_asset_model`, os dois `with transaction.atomic(): write_results(...)` e
`with transaction.atomic(): write_failed(...)` passam a ser
`_write_if_running(run.id, run.asset_id, model_name, lambda r: write_results(r, result, counts))` e o
equivalente com `write_failed`. O `try/except` externo, o "nem o erro pode ser gravado" e a linha de
log continuam; a tarefa **continua nunca levantando**. Quando o `_write_if_running` dos resultados
devolve `False`, o log de retratos mostra `-/-` (nada foi gravado) — `logged = {}`.

### A abertura que não enfileira — literal, em `tasks.py`

```python
def _enqueue_or_close(group: Any, run_id: int, asset_id: int) -> None:
    """O `on_commit` da abertura (RF-11, D-150): enfileira; se o broker recusar, fecha a
    execucao pela regra -- zero resultados, `failed` -- com os pedidos ligados, e levanta."""
    try:
        _enqueue(group)
    except Exception:
        logger.exception("execucao %d: o chord nao foi enfileirado; fechada pela regra", run_id)
        try:
            with transaction.atomic():
                lock_asset(asset_id)
                run = RiskRun.objects.get(pk=run_id)
                now = timezone.now()
                if close_run(run, now) is not None:
                    close_linked(run, now)
        except Exception:
            # o fecho tambem falhou: a linha fica `running`, e a varredura a pega depois
            logger.exception("execucao %d: nem o fecho pela regra foi gravado", run_id)
        raise  # sempre a excecao original, a do broker
```

E em `_abrir_execucao`, `transaction.on_commit(lambda: _enqueue(group))` passa a
`transaction.on_commit(lambda: _enqueue_or_close(group, run.id, asset.id))`. O Django executa o
`on_commit` na saída do `atomic` mais externo, depois do commit, e a exceção do callback sobe dali —
por isso a transação nova dentro do `except`.

### A varredura — contrato, em `stale.py`

```python
@dataclass(frozen=True)
class StaleRun:
    run_id: int
    ticker: str
    calculated_at: datetime
    written: int
    expected: int
    status: str          # o escrito; com dry_run, o que escreveria; com already_closed, o gravado
    already_closed: bool


@dataclass(frozen=True)
class StaleReport:
    runs: list[StaleRun]
    failed: list[tuple[int, str]]   # (run_id, "Tipo: mensagem")
    dry_run: bool

    def render(self) -> str: ...


def _list_stale(now: datetime, older_than: timedelta) -> list[RiskRun]:
    """As presas, avaliadas numa lista: `running` com `calculated_at < now - older_than`."""


def _after_stale_listing() -> None:
    """Ponto de desvio: depois da listagem, antes da trava de cada execucao."""


def close_stale_runs(
    now: datetime, older_than: timedelta, *, dry_run: bool = False
) -> StaleReport: ...
```

`stale.py` importa `close_run` e `count_results` **pelo nome** (`from apps.risk.compute import ...`), e
`tasks.py` importa `close_stale_runs` pelo nome: são os pontos que os testes substituem
(`apps.risk.stale.close_run`, `apps.risk.tasks.close_stale_runs`).

A ordem dentro de `close_stale_runs`, que é o que os testes conferem:

1. a listagem, por `_list_stale` (chamada pelo nome global do módulo):
   `RiskRun.objects.filter(status=RUNNING, calculated_at__lt=now - older_than)`,
   `select_related("asset")`, `order_by("calculated_at")`, **avaliada numa lista antes do laço**. Exceção
   aqui **propaga** (RF-03);
2. para cada execução listada: `_after_stale_listing()`; depois, num `try`, `transaction.atomic()`,
   `lock_asset(asset_id)`, a linha **relida** depois da trava;
   - `expected, written, with_error = count_results(run)`, **sob a trava**, para toda execução
     relida — é daí que saem `written` e `expected` do `StaleRun`, inclusive no `already_closed`;
   - já não `running`: entra como `already_closed=True`, com o status gravado;
   - `dry_run`: `status_for(expected, written, with_error)` entra como o que escreveria; nada é escrito;
   - senão: `close_run(run, now)` (que conta de novo, sob a mesma trava — os números batem);
     `None` → `already_closed=True` com o status relido; status → `close_linked(run, now)`;
3. exceção dentro do `try` de uma execução: `logger.exception` com o id, entra em `failed`, e o laço
   segue.

**O `render` — literal**, porque o comando o imprime e os testes o conferem:

```
{ticker:<12} run={run_id} {calculated_at:%Y-%m-%d %H:%M} {written}/{expected} {status}
{ticker:<12} run={run_id} {calculated_at:%Y-%m-%d %H:%M} {written}/{expected} fecharia {status}   # dry_run
{ticker:<12} run={run_id} {calculated_at:%Y-%m-%d %H:%M} ja fechada ({status})
FALHOU run={run_id}: {erro}
total: {n} fechadas, {m} ja fechadas, {k} falharam       # com dry_run: "{n} fechariam"
```

Sem nenhuma execução listada, o `render` é a linha única `nenhuma execução presa`.

### O comando — `close_stale_runs`

`manage.py close_stale_runs [--dry-run] [--older-than-min N]`, casca sobre `close_stale_runs` no molde
do `compute_risk`: não decide nada. `--older-than-min` ausente usa `settings.RUVOR_RISK_STALE_AFTER`;
`N` menor que `RUVOR_ON_DEMAND_TIMEOUT` em minutos → `CommandError` com as duas grandezas na mensagem.

contagem, **depois** de imprimir; exceção da listagem vira `CommandError` com a mensagem.

### Tarefa 2 — `close_run` condicional e o fecho que respeita

**Depende de:** T1 · **Visual:** não

**Arquivos**
- altera: `backend/apps/risk/compute.py`, `backend/apps/risk/tasks.py` (`_fechar_execucao` e o
  docstring), `backend/apps/risk/models.py` (docstring), `backend/tests/risk/test_presas.py`

**Contrato**
`count_results`, `_after_close_count` e `close_run` literais de *`close_run` condicional*.
`_fechar_execucao`: depois de `close_run`, se devolveu `None`, `logger.info("execucao %d ja fechada
(%s)", run.id, run.status)` e termina; senão `close_linked(run, now)`. Os docstrings do módulo
`compute.py` (linha 40) e de `models.py` (linha 11) passam a dizer que `close_run` só escreve sobre
`running` e que dois caminhos o chamam — o fecho e a varredura — mais a abertura que não enfileira.

**Critério de aceite**
- V-05: linha já `ok` com `finished_at` A; `close_run(run, B)` devolve `None`; relida, `ok` e A; o
  objeto recebido também.
- V-06: execução `running` com dois resultados; fechada `partial` por `close_run(run, A)`; depois

VELHA = timedelta(hours=7)
PRAZO_DA_VARREDURA = timedelta(hours=6)


def test_varredura_e_fecho_concorrentes_um_so_escreve(
    monkeypatch: pytest.MonkeyPatch,
) -> None:
    """V-08 -- guarda do filtro `status=running` do `close_run`. A varredura parte primeiro e
    para dentro da trava, entre a contagem e o UPDATE, esperando 2 s (`ESPERA_QUE_ESTOURA`)
    por um evento que nao chega; o fecho do `chord` parte e bloqueia na trava; a varredura
    escreve e solta; o fecho rele e chama `close_run`, que acha a linha fechada e nao escreve.
    Sem o filtro, o fecho reescreve `status` e `finished_at` e fecha os pedidos."""

    run = _running(asset, timezone.now() - VELHA)
    agora_da_varredura = timezone.now()

    nunca = threading.Event()

    fechou_pedidos: list[int] = []

        # o `close_run` do fecho passa pelo mesmo desvio: so a varredura para
        if threading.current_thread().name != "varredura":
            return
        varredura_contou.set()
        esperas.append(nunca.wait(ESPERA_QUE_ESTOURA))

    def espiao_close_linked(run_: RiskRun, now: datetime) -> int:
        fechou_pedidos.append(run_.pk)
        return 0

    monkeypatch.setattr("apps.risk.tasks.close_linked", espiao_close_linked)

        "varredura",

## Riscos que o plano assume

- **A mutação da trava da varredura em `stale.py`** só é observável com a tarefa concorrente: um teste
  sequencial não a pega. É por isso que o V-08b existe.
- **O avulso e o `worker` dividem o banco de teste.** Uma trilha paralela rodando a suíte ao mesmo
  tempo produz falhas que parecem do código.
- **O V-17 depende do comportamento do transporte Redis** (pré-carregamento e `visibility_timeout`), que
  o plano não mediu; o relato diz o que aconteceu.
