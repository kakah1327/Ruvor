**Spec:** [M1.5 — Execução assíncrona](../specs/M1.5-execucao-assincrona.md)

O relato completo está no [ESTADO](../ESTADO.md#m15--execução-assíncrona). As correções de texto que a execução acumulou estão em [Correções registradas no fecho](#correções-registradas-no-fecho).

Nenhum recusado; o leve do V-10c (ordem de `MODELS` = alfabética) virou risco declarado. As duas primeiras reprovaram; a terceira aprovou, e o médio e os leves dela entraram antes do portão.
**Objetivo:** `compute_risk --async` enfileira uma abertura por ativo; a abertura cria a
`risk_run` no `worker` e dispara um `chord` de uma tarefa por (ativo, modelo), cada uma
gravando os seus dois `risk_result` na própria transação; o fecho lê o banco e escreve
`status` e `finished_at`. O Beat agenda o catálogo e os preços, e o recálculo vem
**encadeado** aos preços.

**Commit por tarefa**, direto na `main` ([D-31](../decisoes/D-31-trabalho-direto-na-main.md)).

## Como ler este plano

[PROCESSO §5](../PROCESSO.md#5-anatomia-de-um-plano): **contratos, não corpos.** Literal só
onde o conteúdo *é* o contrato (nomes de tarefa, colunas, o `beat_schedule`, a regra do
fecho) ou onde a falha é silenciosa (a ordem dos argumentos do `crontab`, o registry nas
tarefas, a transação da tarefa).

Moldes que este plano cita em vez de repetir:

| Para | Copiar de |
|---|---|
| tarefa registrada sem decorador, sob mypy estrito | `backend/config/tasks.py` (`_ping` + `app.task(name=...)(_ping)`) |
| `TextChoices` de estado | `backend/apps/assets/models.py`, `CollectionRun.Status` |
| laço, `_resolve`, relatório, `InvalidTickers` | `backend/apps/risk/compute.py` |
| função chamada pelo nome global para o `monkeypatch` alcançar | `write_risk` em `compute.py` |
| casca com `call_command` nos testes | `backend/tests/risk/test_compute_risk_command.py` |

### Onde cada coisa roda

Tudo no `worker`, como desde o M1.4:

```
docker compose exec -T worker python -m pytest
docker compose exec -T worker python -m mypy .
docker compose exec -T worker ruff check .
docker compose exec -T worker ruff format --check .
```

**Toda tarefa que produz código Python fecha com os quatro**, cada um no seu próprio
`docker compose exec`. No Git Bash, prefixe `MSYS_NO_PATHCONV=1` a qualquer comando com
caminho POSIX do contêiner.

**Nenhuma tarefa toca em `engine/`** ([RF-13](../specs/M1.5-execucao-assincrona.md#rf-13)).

**Critério novo entra com a mutação já exercida** — é a regra que a spec impõe ao próprio
plano. A tarefa que cria um critério aplica a mutação correspondente da tabela da T8 **antes**
de se declarar pronta, registra o código de saída no relato e reverte. A T8 remede todas
juntas; ela confirma, não descobre.

## O que este plano decide

### O estado — `apps/risk/models.py`

```python
class RiskRun(models.Model):
    class Status(models.TextChoices):
        RUNNING = "running"
        OK = "ok"
        PARTIAL = "partial"
        FAILED = "failed"

    ...
    status = models.CharField(max_length=10, choices=Status)   # SEM default
    requested_models = models.JSONField()                      # SEM default, NOT NULL
```

**Nenhuma das duas colunas tem `default` no modelo**, e isso é o que a spec pede no RF-08:
com `default=running`, o caminho síncrono que esquecesse de escrever o estado deixaria a
linha `running` para sempre, em silêncio.

**Tirar o padrão não basta para o `status`, e isso foi medido:** `CharField` sem `default`
tem `get_default() == ""`, então esquecer grava **string vazia** sem erro nenhum. Só o
`requested_models` (`JSONField` → `None`) estoura no `NOT NULL`. Quem guarda o `status` é
teste: a T1 confere que o síncrono grava `ok` e `partial`.

### A migration — `0002_risk_run_status_e_modelos.py`

Três operações, nesta ordem:

1. `AddField(status, default="ok", preserve_default=False)`
2. `AddField(requested_models, default=list(MODELS), preserve_default=False)` — a lista
   escrita **literalmente** na migration, não importada de `compute.py`: migration não pode
   importar código que importa o motor, senão a `web` deixa de conseguir rodar `migrate`
3. `RunPython(backfill, reverse_code=RunPython.noop)`, que **deriva do dado** cada linha
   existente:
   - `requested_models` = os `model_name` distintos dos `risk_result` da linha, **na ordem de
     `MODELS`**
   - `status` = a regra do fecho (abaixo), com `esperado = len(requested_models) * 2`

**Por que derivar e não carimbar.** O M1.4 grava modelo que falha como linha com `error`, então
os nomes dos resultados de uma execução do M1.4 **são** o que ela pediu — inclusive numa
execução com `--model`. Carimbar "os nove, `ok`" acertaria as oito linhas do banco real e
mentiria sobre qualquer banco com uma execução parcial. **Para as oito medidas, a derivação
dá exatamente o que a spec manda: `ok` e os nove.** O V-10c confere os dois casos.

### A regra do fecho — literal, em `compute.py`

```python
def status_for(expected: int, written: int, with_error: int) -> str:
    if written == 0 or with_error == written:
        return RiskRun.Status.FAILED
    if written == expected and with_error == 0:
        return RiskRun.Status.OK
    return RiskRun.Status.PARTIAL
```

Uma função pura, usada pelos **três** lugares que decidem estado: o fecho assíncrono, o
caminho síncrono e o `backfill` da migration (que a copia, porque migration não importa
`compute.py` — ver acima; um teste confere as duas contra a mesma tabela de casos).

### `compute.py` — o laço passa a servir os dois caminhos

O caminho síncrono **não muda de forma**: continua uma transação por ativo, e
`write_risk(asset, calculated_at, finished_at, seed, bars, result)` **mantém a assinatura**
— o V-10 do M1.4 a substitui por `monkeypatch`, e é o teste que prova a transação síncrona.
Ela passa a gravar, na criação:

- `requested_models = result.config.model_names`
- `status = status_for(len(model_names) * 2, len(result.runs), com_erro)` — calculado **antes**
  do `create`, a partir de `result.runs`. **O síncrono não faz `UPDATE`**: sabe o desfecho
  antes de escrever

O que se separa para as tarefas usarem, todas chamadas **pelo nome global**:

```python
def open_run(asset, calculated_at, seed, bars, models) -> RiskRun
    # status=RUNNING, finished_at=None, requested_models=models; o resto do manifesto como
    # write_risk ja monta (engine_version, datas, contagens, price_run)
def write_results(run, result: ExperimentResult) -> None      # bulk_create de _row(...)
def write_failed(run, model_name, error: str) -> None         # as DUAS linhas do modelo,
                                                              # uma por alpha, error preenchido
def close_run(run, finished_at) -> str                        # conta no banco, status_for,
                                                              # UPDATE de status e finished_at
```

`write_risk` **não** é montada sobre `open_run` + `write_results`: ela cria a linha já com o
estado final, e reusar `open_run` a obrigaria a um `UPDATE` de que o síncrono não precisa. As
duas compartilham a montagem do manifesto por uma função privada
(`_manifest(asset, calculated_at, seed, bars) -> dict`), e é só. **`_manifest` não recebe o
`ExperimentResult`**, então o `train_window_days` passa a sair de `config.TRAIN_WINDOW_DAYS`,
não de `result.config` — é o mesmo valor hoje, porque o `ExperimentConfig` é montado com a
constante, mas é uma mudança de origem e fica dita.

**`write_failed` grava números nulos e `error` preenchido**, exatamente como `_row` faz quando
o `ModelRunResult` traz erro: `model_category` e `hyperparameters` saem de
`get_model(model_name)`, como hoje. É o que mantém a distinção "falhou × reprovado" que o M1.4
construiu.

### As tarefas — `apps/risk/tasks.py`

Nomes de registro **explícitos**, molde de `config/tasks.py`: função com sublinhado +
`app.task(name=...)(função)`. `app` vem de `config.celery`.

| Tarefa registrada | Função | Levanta? |
|---|---|---|
| `apps.risk.tasks.abrir_execucao` | `_abrir_execucao(ticker, calculated_at_iso, seed, models) -> int \| None` | **pode** — é a única ([spec, "Se a abertura falhar"](../specs/M1.5-execucao-assincrona.md#as-sete-tarefas-e-quem-chama-quem)) |
| `apps.risk.tasks.compute_asset_model` | `_compute_asset_model(run_id, model_name) -> None` | **nunca** (RF-06) |
| `apps.risk.tasks.fechar_execucao` | `_fechar_execucao(_resultados, run_id) -> None` | não deveria; não há regra |
| `apps.risk.tasks.recalcular_cobertos` | `_recalcular_cobertos(calculated_at_iso=None) -> None` | pode |

E duas funções que **não** são tarefa:

```python
def enqueue_compute(
    tickers, *, seed=None, models=None, calculated_at: datetime | None = None,
    now=timezone.now,
) -> AsyncReport
    # o que o `--async` e o `recalcular_cobertos` compartilham: registry, _resolve,
    # calculated_at UMA vez (o recebido, ou now()), e um _enqueue(abrir_execucao.s(...))
    # por ativo ativo
def _enqueue(signature) -> None:   # signature.apply_async(); o ponto do monkeypatch
```

**`_abrir_execucao`, passo a passo:**

1. `load_all_model_modules()` e `load_all_backtest_modules()` — ver "O registry nas tarefas"
2. `bars = _bars(asset)`; abaixo de `MIN_SESSIONS` **devolve `None`**, loga o motivo e não
   cria linha — pulo silencioso, como no síncrono
3. `run = open_run(...)`, com `calculated_at = datetime.fromisoformat(calculated_at_iso)`
4. monta o `chord` **sem aplicar** e o entrega ao `_enqueue` — a forma `chord(...)(corpo)`
   que a spec cita **já aplica**, e com ela nenhum duplo conseguiria capturar nada:
   ```python
   _enqueue(chord([compute_asset_model.si(run.id, m) for m in models],
                  fechar_execucao.s(run.id)))
   ```
   O cabeçalho usa `.si()` (imutável) porque não há o que receber; o corpo usa `.s()` porque
   **recebe** a lista de resultados do cabeçalho como primeiro argumento — é o `_resultados`
   da assinatura
5. devolve `run.id`

**`_compute_asset_model`, passo a passo — e o `try` cobre os passos 2 a 6:**

1. `run = RiskRun.objects.get(pk=run_id)` — se isto falha, loga e devolve; não há onde
   gravar
2. **idempotência**: se já existe `risk_result` para `(run, model_name)`, devolve sem gravar
   — repetição do Celery não duplica nem levanta `IntegrityError`
3. registry carregado (ver abaixo)
4. `bars` = `_bars(run.asset)` **restrito a `[run.first_price_date, run.as_of_date]`**; se
   `len(bars) != run.price_count`, levanta `SeriesChanged("serie mudou desde a abertura: N
   pregoes, esperados M")` — exceção própria do módulo —, e o passo 7 a transforma no par de
   erro. O `error` gravado é portanto **exatamente** `"SeriesChanged: serie mudou desde a
   abertura: N pregoes, esperados M"`, e o teste compara por igualdade
5. `run_experiment` com `model_names=[model_name]`, os dois níveis, `seed=run.seed`,
   `train_window_days=run.train_window_days`, `start`/`end` = as datas da linha
6. `with transaction.atomic(): write_results(run, result)`
7. **qualquer exceção** dos passos 2–6 → `with transaction.atomic(): write_failed(run,
   model_name, f"{type(exc).__name__}: {exc}")`; se **isso** também levantar, loga e devolve.
   A tarefa termina normalmente em todos os ramos

O passo 4 é decisão deste plano, não da spec: a spec diz que a linha "é a fonte de verdade", e
uma tarefa que lesse a série de hoje para uma execução aberta ontem gravaria números de uma
série diferente da que o manifesto descreve — **sem erro nenhum**. Restringir pela janela
resolve pregão novo; a conferência da contagem torna alto o caso raro de reconformação no
meio (a [D-53](../decisoes/D-53-evento-novo-rebusca-a-serie-inteira.md) reescreve a série
inteira quando chega evento). Reescrita de valor com a mesma contagem continua invisível — e
fica registrada como risco, não resolvida.

**`_fechar_execucao`:** `close_run(RiskRun.objects.get(pk=run_id), timezone.now())`. Ignora
`_resultados` — lê o banco (RF-05).

**`_recalcular_cobertos`:** `enqueue_compute([], calculated_at=...)` — sem tickers, o ramo
"os ativos com preço" do `_resolve`. `calculated_at_iso` nulo → `None` passado adiante, e
`enqueue_compute` faz o `now()` **uma vez**.

### O registry nas tarefas — a armadilha do `_REGISTRY`

**`_abrir_execucao` e `_compute_asset_model` chamam `load_all_model_modules()` e
`load_all_backtest_modules()` antes de tocar no motor**, importadas **pelo nome** em
`apps/risk/tasks.py` (`from engine.models import load_all_model_modules`) e chamadas pelo
nome global. O processo-filho do *prefork* nasce sem o registry populado; o `compute_risk`
síncrono sempre o carregou porque passa por `run_compute_risk`.

Isto é o [aprendizado do M1.4](../aprendizados.md#_registry-do-motor-é-global-de-processo-e-isso-esconde-mutação)
em outra roupa: **mirar a mutação na suíte comum passa verde**, porque qualquer teste
anterior já populou o dicionário global. E a execução real também não é boa guarda: com
`--concurrency=2`, o filho que rodou uma abertura já carregou o registry para as tarefas que
vierem depois nele, então a omissão só em `_compute_asset_model` provavelmente passaria.

**A guarda é o molde que o M1.4 já tem**, `test_o_registry_e_carregado_antes_de_ser_consultado`
(`tests/risk/test_compute.py`): espiões em `apps.risk.tasks.load_all_model_modules` e
`apps.risk.tasks.load_all_backtest_modules` provam que **cada uma** das duas funções de
tarefa os chama, antes do motor. A T3 o escreve; a mutação morde nele.

### O comando — `--async`

`compute_risk [TICKER ...] [--seed N] [--model NOME ...] [--async]`. Com `--async`, a casca
chama `enqueue_compute` e imprime o `AsyncReport`. Dos três erros do síncrono, **dois**
valem aqui, com as mesmas mensagens e **código 1**: `InvalidTickers` e `ModelsMissing` — o registry é conferido
**antes** de enfileirar, porque o comando roda no `worker` e a regra do RF-17 vale nos dois
caminhos. `RiskFailed` não existe no assíncrono: o comando não espera resultado.

**O relatório, literal** — a spec manda imprimir os tickers resolvidos e quantas aberturas,
nunca `run_id`:

```
IBOV         enfileirado
PETR4        enfileirado
BAZZ4        pulado: inativo
risco assincrono: 3 ativos, 2 enfileirados, 1 pulados; acompanhe em gold.risk_run
```

Alinhamento de 12 colunas no ticker, plural invariável, como o M1.3 fixou. **Nenhum ativo
enfileirado** — sem candidato nenhum, ou, no ramo sem argumentos, só inativos —, a saída
repete o síncrono: as linhas de pulado, se houver, e depois `nenhum ativo ativo com preco;
informe tickers` (a mesma constante `NO_CANDIDATES`), **sem** a linha de resumo. Nada é
enfileirado, código 0.

### As tarefas de coleta — `apps/assets/tasks.py`

| Tarefa registrada | Função |
|---|---|
| `apps.assets.tasks.importar_ativos` | `_importar_ativos() -> str` — `call_command("import_assets", stdout=buf)`; devolve o texto |
| `apps.assets.tasks.importar_precos` | `_importar_precos() -> str` — idem com `import_prices`; **captura `CommandError`** e devolve `"FALHOU: " + mensagem`. Qualquer outra exceção propaga |
| `apps.assets.tasks.rotina_diaria` | `_rotina_diaria() -> None` — `_enqueue(chain(importar_precos.s(), recalcular_cobertos.si()))`, com um `_enqueue` **próprio de `apps/assets/tasks.py`**, não importado de `apps.risk.tasks` — é `apps.assets.tasks._enqueue` que o V-09 substitui |

`call_command` é importado **pelo nome** no módulo (`from django.core.management import
call_command`) e chamado pelo nome global — é o ponto que o V-10b substitui.

**`recalcular_cobertos.si()`, não `.s()`**: com `.s()`, o texto devolvido por
`importar_precos` chegaria como `calculated_at_iso`, e `datetime.fromisoformat("listagem: ...")`
estouraria. É a mesma falha que a spec descreve no RF-09, com a consequência concreta.

`apps.assets.tasks` importa `apps.risk.tasks`. Não cria ciclo — `apps.risk` importa
`apps.assets.models`, não `apps.assets.tasks` —, e só roda no `worker` e no Beat, que têm o
motor.

### O Beat — `settings.py`

```python
def _cron(name: str, default: str) -> crontab:
    # `or`, nao o segundo argumento do get: o compose passa a variavel VAZIA quando o .env
    # nao a define (ver "A infraestrutura"), e vazio tem de valer o padrao
    fields = (os.environ.get(name) or default).split()
    if len(fields) != 5:
        raise ImproperlyConfigured(f"{name}: esperados 5 campos de cron, veio {len(fields)}")
    minute, hour, day_of_month, month_of_year, day_of_week = fields
    return crontab(minute=minute, hour=hour, day_of_month=day_of_month,
                   month_of_year=month_of_year, day_of_week=day_of_week)

CELERY_BEAT_SCHEDULE = {
    "catalogo": {"task": "apps.assets.tasks.importar_ativos",
                 "schedule": _cron("RUVOR_BEAT_ASSETS_CRON", "0 7 * * 1")},
    "precos":   {"task": "apps.assets.tasks.rotina_diaria",
                 "schedule": _cron("RUVOR_BEAT_PRICES_CRON", "30 19 * * 1-5")},
}
```

**A armadilha que justifica o literal: a ordem posicional do `crontab` não é a do cron.** O
construtor é `crontab(minute, hour, day_of_week, day_of_month, month_of_year)` — o dia da
semana vem em **terceiro**. Quem fizer `crontab(*valor.split())` sobre `"30 19 * * 1-5"`
entrega o terceiro campo do cron (dia do mês, `*`) como dia da semana e o quinto (dia da
semana, `1-5`) como **mês**: a agenda passa a ser "todo dia, de janeiro a maio", e ninguém
percebe até junho. Por isso **argumentos nomeados, sempre**, e o V-10 confere um valor em que
as duas leituras divergem.

**Os padrões são chute declarado** (RF-11): catálogo segunda às 7h, preços de segunda a
sexta às 19h30, no fuso de São Paulo, que o Celery já herda (medido). Entram iguais no
`.env.example`.

### A infraestrutura — `compose.yaml`

- `worker` ganha `command: celery -A config worker --loglevel=info --concurrency=2` (RF-12).
  O `CMD` do `Dockerfile` **não muda** — o arquivo não está no inventário, e o `command:`
  sobrepõe
- serviço novo **`beat`**: `image: ruvor-worker`, **sem `build`** — reusa a imagem que o
  `worker` constrói, em vez de produzir uma segunda de 3,8 GB; `command: celery -A config
  beat --loglevel=info`; `depends_on` do `redis` saudável; e **`pull_policy: never`**. O
  `depends_on` ordena contêineres, não o *build* — sem o `pull_policy`, o compose tenta
  primeiro baixar `ruvor-worker` de um registro público — medido na revisão: o `up` imprime
  `pull access denied`, **tolera** e sai 0. O `never` não evita falha, evita o download
  tentado e o erro no log a cada subida: o Beat usa a imagem que o `--build` do `worker`
  produz, ou falha alto com `No such image` se ela faltar
- **o Beat monta `./engine` também**, como o `worker`. Não calcula nada, mas **importa**:
  na partida, `celery beat` chama `loader.init_worker()` → `import_default_modules()`, e a
  descoberta automática importa `apps.risk.tasks` → `apps.risk.compute` → `engine`. A
  imagem instala o motor em modo editável e só copia o `pyproject.toml` e o `__init__.py`
  dele — **sem a montagem, `import engine.backtesting` dá `ModuleNotFoundError` e o Beat
  morre na partida** (medido na revisão com `docker run --rm ruvor-worker`). A sonda do plano
  que viu o Beat subir rodou dentro do `worker`, que tem a montagem, e por isso não pegou
- **as duas variáveis de horário entram no `environment` do `beat`**, e só nele, por
  mesclagem sobre o âncora:
  ```yaml
  environment:
    <<: *backend-env
    RUVOR_BEAT_ASSETS_CRON: ${RUVOR_BEAT_ASSETS_CRON:-}
    RUVOR_BEAT_PRICES_CRON: ${RUVOR_BEAT_PRICES_CRON:-}
  ```
  O `.env` do compose **só serve para interpolação**: variável que não é nomeada no
  `environment` não chega ao contêiner, e o RF-11 ficaria sem efeito no ambiente real. O
  `:-` vazio mantém o padrão num lugar só, o `settings.py` — por isso o `_cron` trata vazio
  como ausente. Só o `beat` as recebe porque só o Beat lê a agenda
- `healthcheck` do Beat na forma **`["CMD", "python", "-c", "<codigo>"]`**, nunca
  `CMD-SHELL`, e com o código **sem `$`** — a forma que a T7 sabe executar fora do Docker
  (ver lá). Duas condições: **(1)** o
  `celerybeat-schedule` modificado há menos de *N* segundos e **(2)** conexão com o broker

  nada depois da primeira partida, mas o `Scheduler` sincroniza o arquivo periodicamente.
  **O período e se o `mtime` avança mesmo sem entrada vencida são medidos na T7**, e *N* sai
  dessa medição com folga. Se o `mtime` não avançar sem tique, a (1) sai e o plano volta a
  dizer que o laço não é provado. Tempos: `interval: 30s`, `timeout: 20s` — acima dos 10 s da

**Antes de fixar o `healthcheck`**, medir no Beat de pé: o intervalo com que o `mtime` do
`celerybeat-schedule` avança **sem** entrada vencida (a agenda padrão não vence durante a
medição). O *N* da condição (1) sai dessa medição com folga de pelo menos 2×; o número vai
para o relato e para o comentário do `compose.yaml`.

O `healthcheck` **sabendo reprovar**, nas duas condições, pelo **código de saída do próprio
comando** — extraído de `docker compose config --format json`
(`services.beat.healthcheck.test`) e executado com `docker compose exec -T beat`, para que o
que se mede seja o que está no `compose.yaml`, não uma cópia. **A receita:** um script Python
no hospedeiro lê o JSON, confere `test[0] == "CMD"`, e passa `test[1:]` como argv ao
`exec` — sem `sh -c`, e por isso sem desescapar nada (o `config` mantém `$$` escapado, e um
`CMD-SHELL` extraído rodaria outro comando que o real). Extrair do `config`, e não do
`docker inspect`, é o que deixa a T8 medir a mutação editada no `compose.yaml` **sem recriar
o contêiner**:

- **(2)**: `docker compose stop redis` → o comando sai ≠ 0; `start redis` → sai 0
- **(1)**: `docker compose exec -T beat touch -d '1 hour ago' celerybeat-schedule` → o
  comando sai ≠ 0 **imediatamente**, com o processo do Beat vivo; o próximo *sync* do Beat
  devolve o 0 — com o Beat ocioso, até ~300 s depois (o `tick` devolve até `max_interval`, e
  o *sync* só roda depois do `sleep`; os 180 s de `sync_every` são piso, não período)

**Não usar `docker compose pause`, e o motivo foi medido na revisão:** o Docker marca
contêiner pausado como `unhealthy` por conta própria, com qualquer `healthcheck` — inclusive
um que seja literalmente `true` —, e ao despausar o Beat sincroniza quase na hora, porque o
relógio monotônico continuou correndo. O `pause` aprovaria a condição (1) e também a mutação
que a remove. Nem o estado `unhealthy` do Docker serve de critério aqui: ele depende de
`retries × interval` (150 s) caber antes do próximo *sync* (até ~300 s com o Beat ocioso),
o que é corrida, não prova.

**E o `pull_policy: never` provado com a imagem ausente**, uma vez: `docker compose down`,
`docker image rm ruvor-worker`, `docker compose up -d --build --wait` → seis saudáveis. Não é
máquina limpa — o cache do BuildKit sobrevive e a reconstrução sai quase toda dele —, mas o
que se prova é a imagem faltar na hora do `up`, e isso vale.

**Ao fim, `docker compose stop beat`.** Com o Beat de pé, a agenda padrão dispararia
`import_prices` real e o recálculo às 19h30 de qualquer dia útil em que a T8 ou a T9
estivessem rodando — e a medição 2 da T9 **depende** de `silver.price` intocada desde o
M1.4. O Beat só volta na medição 4 da T9.

**Cerca de escopo**
Não mexe no `Dockerfile` nem no `ci.yml` — a CI sobe só `worker` e `frontend`, e o Beat não
tem o que provar numa máquina sem dado.

## Riscos que o plano assume

- **Reescrita de valor com a mesma contagem** entre a abertura e a tarefa passa sem acusar
  (ver "`_compute_asset_model`, passo 4"). A rotina diária encadeia coleta e cálculo, então
  não há concorrência entre os dois no caminho normal; o `--async` manual rodado no meio de
  uma coleta é o caso que sobra.
- **O V-10c não executa a migration em teste**: prova a função, a forma da lista de
  operações e, na T9, o dado real. Uma migration que a executasse de ponta a ponta exigiria
  `transaction=True`, que esvazia o banco para os testes seguintes — ver a T1.
- **O `healthcheck` do Beat depende de uma medição da T7** (o `mtime` avança sem tique?). Se
  não avançar, ele volta a provar só a partida e o broker, e o plano diz isso. A prova da
  condição (1) é o `touch -d` sobre o arquivo, **nunca** o `pause` do contêiner.
- **O teste (a) do V-10c não distingue "ordem de `MODELS`" de "ordem alfabética"**, porque
  `MODELS` é alfabético. O resultado exigido é o certo nos dois casos; o mecanismo fica sem
  guarda, e não há hoje como as duas ordens divergirem.
